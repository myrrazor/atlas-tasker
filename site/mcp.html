For AI agents

Give every agent a real seat.

Atlas Tasker is the ticketing system for your entire life and your AI agents. OpenClaw, Codex, Claude Code, Hermes: if it speaks MCP or can run a shell, it can read the board, claim work, attach evidence, and request review. Humans keep the approvals that matter.

Two doors in

A JSON CLI and a typed MCP server.

Both doors call the same service layer, so neither is a second source of truth. Shell-capable agents get the full CLI. Clients without a shell get MCP.

  • CLI + --json

    Every command emits exactly one JSON document on stdout, errors go to stderr as JSON, and exit codes 0 through 7 are stable. Nothing prompts, ever. The CLI page has the contract.

  • MCP server

    tracker mcp serve exposes 63 typed tools over local stdio. No HTTP server, no remote clients, no shell strings built from tool input. Every mutation still runs Atlas permission checks, the write lock, and event metadata.

  • Self-describing

    Every tool declares its underlying_atlas_action and a json_schema_hash, and calls are validated against the schema before they touch the tracker. Unknown arguments are rejected at the boundary.

  • Context budgets

    Responses are capped by default at 128 KB, 50 items per list, and a rough 4,000-token estimate. Paged tools take limit and cursor, and oversized results come back truncated with a hint to narrow the call.

Permission profiles

63 tools on an escalating ladder.

Start the server with the smallest profile that does the job. Each rung adds tools on top of the previous one, and the dangerous rung stays invisible until a human turns two separate keys.

  1. read

    34 tools · the default

    Boards, queues, tickets, schedules, history, runs, evidence, handoffs, sync status, and every plan/dry-run tool. No writes at all.

  2. workflow

    +13 tools · actor + reason required

    Safe mutations: comment, claim, release, move, set or clear ticket schedules, request review, approve or reject gates, checkpoints, evidence, handoffs, import preview.

  3. delivery

    +4 tools · live side effects

    Dispatch a run, create a change, and sync provider-backed change and check status into the tracker.

  4. admin

    +12 tools · hidden by default

    Merges, gate waivers, ticket completion, sync push and pull, imports, archive, compact, worktree cleanup. Requires the flag and a one-time human approval per call.

Inspect what any profile actually exposes before you trust it: tracker mcp tools --json --tool-profile read

The safety model

Agents can do everything. Except quietly.

The point is not to keep agents out. It is to make every risky action explicit, attributable, and approved by a human before it lands.

  • Hidden by default

    High-impact tools are not just denied, they are invisible unless the server was started with --dangerously-allow-high-impact-tools and a profile that includes them. Agents cannot ask for what they cannot see.

  • One-time approvals

    Each high-impact call needs an approval a human created outside MCP with tracker mcp approve-operation, scoped to one operation, one target, one actor, with a TTL. The call must echo the approval id and its exact confirm_text.

  • Single use

    Approvals are consumed on execution and never replayed. Expired, mismatched, or already-used approvals fail closed, and Atlas rechecks normal policy immediately before running the action.

  • Attributed writes

    Every mutation names an actor and a reason, which land in the append-only event log. When a ticket moved, you can always answer who, when, and why.

  • Audited denials

    Denied high-impact attempts are recorded to a local security audit log under .tracker/runtime/mcp/, so a curious agent leaves a paper trail instead of a mystery.

  • Boring config

    Local stdio only, pinned to an absolute binary path. No sh -c, no npx, no curl pipes, no config snippets from untrusted repos. The security docs spell out the rules.

Hook it up

Three clients, one line each.

Use an absolute path to the tracker binary, and always pin --workspace for user-scoped or global registrations. The client picks the working directory, not you, and --workspace is what stops the server from answering against the wrong repo.

Claude Code · user scope
claude mcp add --transport stdio --scope user atlas -- /usr/local/bin/tracker mcp serve --workspace /path/to/repo --tool-profile read
Codex
codex mcp add atlas -- /usr/local/bin/tracker mcp serve --workspace /path/to/repo --tool-profile read
OpenClaw · --cwd pins the directory
openclaw mcp add atlas --command /usr/local/bin/tracker --arg mcp --arg serve --cwd /path/to/repo

Other MCP clients follow the same shape: absolute binary, mcp serve, a pinned workspace, and the read profile until a human asks for writes.

Teach the loop

One installer writes the playbook.

Agents work best when the workflow is written down where they read. Atlas ships an installer that drops an atlas-worker skill and instruction block into the right place for each runtime.

pick your runtime
tracker integrations install claude     # .claude/skills/
tracker integrations install codex      # .codex/skills/
tracker integrations install openclaw   # .agents/skills/
tracker integrations install generic    # .tracker/integrations/

Re-running is safe. Only the Atlas-managed block between markers changes, and whole-file replacement is opt-in behind --force.

  • The working loop

    Ask tracker agent available <id> --json for what is ready. Claim it, move it to in progress, comment as you go, request review when done. A reviewer approves and completes. Every step is one command.

  • Suggested commands

    The queue does the thinking: each available item includes suggested_commands, the exact claim-and-move invocations for that agent, ready to execute verbatim.

  • Reason codes

    When nothing is available, tracker agent pending says why with stable codes: dependency_blocked, waiting_for_review, waiting_for_owner, not_ready_status, claimed_by_other, policy_blocked, agent_at_capacity, missing_capability. No guessing, no polling loops that spiral. A backlog ticket whose blockers are all done is never not_ready_status: when the last blocker of an agent-assigned ticket completes, Atlas promotes it to ready itself, and an unassigned one shows up in available as a claimable promote action (a human-assigned one surfaces in that human's queue instead).

  • Wrong moves fail fast

    Illegal status transitions exit 4. Claiming a ticket someone else holds exits 4. That is the workflow enforcing itself, and the agent simply picks the next available item.

tracker agent available builder-1 --json

One boundary

The web board is for humans.

The browser board mints a random session token per process and never persists it. There is no API key and no headless mode, on purpose. Agents get the CLI and MCP, which are better interfaces for them anyway. Point people at the board and agents at the tools, and everyone works the same tickets.

Agents

MCP setup

Atlas ships a local stdio MCP server for clients that want typed tools instead of a shell. It calls the same service layer as the CLI, so it is never a second source of truth: every mutation still runs permission checks, the write lock, and event metadata.

Start the server

serve, inspect, approve
tracker mcp serve --tool-profile read
tracker mcp serve --workspace /path/to/repo --tool-profile read
tracker mcp tools --json --tool-profile read     # what does this profile expose
tracker mcp schema --json --tool-profile workflow

serve reads the current directory unless --workspace names one. That flag is load-bearing: user-scoped and global registrations start wherever the client happens to be, and without --workspace the tools answer against that directory. It is the usual reason a tool returns not_found for a ticket you can see in your terminal. A workspace that does not exist or was never through tracker init fails at startup naming the path it tried.

Profiles

Four escalating profiles decide which of the 59 tools exist in a session. Start at read and widen only when the human asks for writes.

ProfileToolsAdds
read32Reads and plan/dry-run tools only. The default.
workflow+11Comments, claims, moves, request review, gate approve/reject, checkpoints, evidence, handoffs, import preview. Actor and reason required.
delivery+4Dispatch, change create, change sync, checks sync. Live side effects.
admin+12High-impact operations, hidden unless the server also runs with --dangerously-allow-high-impact-tools. See MCP security.

Client setup

Claude Code

user scope: pin the workspace
claude mcp add --transport stdio --scope user atlas -- /usr/local/bin/tracker mcp serve --workspace /path/to/repo --tool-profile read

Project-scoped servers already launch in the project directory, so --workspace becomes optional there. Check status inside Claude Code with /mcp.

Codex

cli or config.toml
codex mcp add atlas -- /usr/local/bin/tracker mcp serve --workspace /path/to/repo --tool-profile read

# or in config.toml
[mcp_servers.atlas]
command = "/usr/local/bin/tracker"
args = ["mcp", "serve", "--workspace", "/path/to/repo", "--tool-profile", "read"]

OpenClaw

--cwd pins the directory
openclaw mcp add atlas --command /usr/local/bin/tracker --arg mcp --arg serve --cwd /path/to/repo

Any other MCP client follows the same shape: absolute binary path, mcp serve, a pinned directory, and the read profile until writes are wanted.

Response budgets

Tool results are capped so a big board cannot flood a model's context. The defaults are 128 KB per result, 50 items per list, and a rough 4,000-token estimate for the text fallback. Tune them per server:

tighter budgets for smaller contexts
tracker mcp serve \
  --tool-profile read \
  --max-result-bytes 131072 \
  --max-items 50 \
  --max-text-tokens-estimate 4000
  • Paged list tools accept limit and cursor, and payloads return total, next_cursor, and truncated.
  • Grouped reads keep independent cursors: atlas.board takes cursor_by_status and atlas.dashboard takes cursor_by_section, so a short column never disappears because a long one advanced.
  • Oversized results come back as a truncated summary with a hint to narrow the call instead of a silent cut.

What a tool call looks like

same envelope as the CLI
{
  "format_version": "v1",
  "kind": "atlas.ticket.view",
  "generated_at": "2026-05-05T12:00:00Z",
  "payload": {}
}

Every tool also declares the underlying_atlas_action it maps to and a json_schema_hash for its arguments, and calls are validated against that schema before they reach the tracker. Unknown arguments and wrong JSON types are rejected at the adapter boundary. Mutating tools require actor and reason in the arguments, exactly like the CLI flags.

Continue with MCP security for the high-impact approval flow, and JSON and exit codes for the error envelope shared by both surfaces.

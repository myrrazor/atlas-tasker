# ADR: Unified Setup and Transaction Model (AT114-002)

Status: Sprint 114.0 architecture decision, frozen for independent design review. Recorded as
DEC-070 in [v1-decision-log.md](v1-decision-log.md). Implemented by Sprint 114.1
(AT114-101..106) on top of the adapter contract in
[v1.14-provider-adapter-contract.md](v1.14-provider-adapter-contract.md) and the operation state
machine in `internal/setup/operation.go`.

## 1. Decisions

1. **`tracker init` stays low-level.** It initializes a workspace (config, identity, directories)
   and keeps its existing `--integrations` / `--skip-integrations` behavior in v1.14. It never
   registers MCP servers, never touches client configuration, never configures backup.
2. **`tracker setup` is the orchestrator.** It composes: workspace inspection, six-target
   detection, planning, consent, per-provider transactions, managed-mode policy, optional backup
   configuration, verification, and the local setup manifest. It never installs agent software and
   never initializes a directory that is not already a workspace unless the user explicitly asks
   through the existing `init` path first.
3. **Read-only plan first, always.** Every run (interactive, `--yes`, `--json`, `--plan`) begins by
   producing a complete validated `IntegrationPlan` per selected target plus the managed-mode and
   backup plans. `--plan` stops there. Nothing is written until every plan validates and consent is
   recorded; a plan that fails validation aborts the whole run before the first write.
4. **One transaction per provider.** Each provider integration is its own transaction with its
   own journal entry, snapshots, and rollback. A failure in one rolls back only that provider; the
   others keep their `connected`/`pending_*` result. Partial success is reported as such, with the
   exact per-provider state, never collapsed into a single "setup failed".
5. **Backup is a separate transaction group with separate consent.** It is planned in the same run
   but consented, applied, and reported independently (locked decision 6). A backup failure never
   rolls back agent integrations; an integration failure never prevents backup configuration.
6. **Idempotent.** Re-running setup against a workspace that already matches produces `NoOp` plans
   and writes nothing, including no journal entry and no manifest rewrite.
7. **Repair and removal reuse the adapter contract.** `Repair` and `Remove` return plans of the
   same shape (`Operation = repair | remove`) that run through the same journal. There is no second
   code path for undoing setup.
8. **No global provider state without explicit consent.** Default scopes are the project-bound
   ones in the capability matrix. Any user-level or gateway-level write (Claude `--scope user`,
   Codex `~/.codex/config.toml`, Cursor `~/.cursor/mcp.json`, Grok `~/.grok/config.toml`, OpenClaw
   gateway) requires the user to have chosen that scope explicitly in the plan; OpenClaw's only
   scope is gateway, so selecting OpenClaw is that consent, and the plan says so.
9. **Provider trust dialogs are never bypassed.** Approval requirements become `ApprovalStep`s that
   are reported and awaited; the resulting integration state is `pending_workspace_trust` or
   `pending_mcp_approval` until `Verify` proves otherwise. Atlas never edits a client's trust or
   approval records (`~/.claude.json` project approvals, Codex `projects.<path>.trust_level`,
   Cursor enterprise allowlists, `disabledMcpjsonServers`).
10. **No agent software is installed.** Detection finds what is on the machine; a missing client
    yields a `Detection{Installed: false}` and, at most, a skill/instruction-only plan.

## 2. Operation states

`internal/setup.OperationState` is the closed set from the plan, in this order:

```text
planned  applying  applied  verifying  connected  pending_approval
failed   rolling_back  rolled_back  repair_required
```

Legal edges (`OperationState.Allows`, tested in `operation_test.go`):

```text
planned          -> applying
applying         -> applied | rolling_back | failed
applied          -> verifying | rolling_back
verifying        -> connected | pending_approval | repair_required | rolling_back | failed
connected        -> verifying | repair_required
pending_approval -> verifying | repair_required | rolling_back
failed           -> rolling_back | planned
rolling_back     -> rolled_back | failed
rolled_back      -> planned
repair_required  -> planned
```

Properties the tests pin:

- Nothing reaches `applying` without `planned` (no write before a complete plan).
- Nothing reaches `connected` or `pending_approval` except through `verifying` (verification is
  never skipped, and a pending approval is re-verified rather than assumed).
- `failed` never moves to `connected`; it goes back to `planned` (a fresh plan) or to
  `rolling_back`.
- `rolled_back` and `planned` are the only states that guarantee no writes remain
  (`MayHaveWritten() == false`).
- A journal re-mark to the same state is allowed (resume) and is not a transition.

The operation state is distinct from the adapter's integration state: the operation says where
the transaction is, the integration state says what it produced. `connected` (operation) covers
both `connected` and `connected_restart_required` (integration); `pending_approval` covers
`pending_workspace_trust`, `pending_mcp_approval`, and `configured_unverified` /
`portable_ready` when a human step or client is still outstanding.

## 3. Transaction protocol (per provider)

```text
1. acquire setup lock (machine-local, in the private state directory; not the workspace write lock)
2. validate every target path: inside workspace or consented root, not a symlink, parent exists
   or is creatable, no NUL, expected format parses if the file exists
3. journal: planned  (plan fingerprint, target, workspace ID, step list)
4. for each step, in order:
     a. record FileIdentity{exists, mode, size, sha256} of the path (never contents into the journal)
     b. copy the pre-write file into private rollback material (0600) when the step is reversible
     c. journal: applying (step started)
     d. perform the step (atomic write: temp file + fsync + rename; or run the structured Command)
     e. journal: step applied (post-write FileIdentity)
5. journal: applied
6. journal: verifying; run Verify
7. journal: connected | pending_approval | repair_required | failed
8. on success: write the IntegrationState record into the local setup manifest (0600) and only
   then delete or rotate rollback material according to retention
9. release setup lock
```

Failure at any step in 4–7 moves to `rolling_back`, runs the `Rollback` action of every started
step in reverse order (`restore_snapshot` from the private copy, `delete_created`, or the
structured `run_command` for client CLIs), and ends `rolled_back` (or `failed` when a rollback
action itself fails, in which case the journal lists the exact paths left for the operator).

Irreversible steps are refused unless the plan classified them `irreversible` with a reason and
the user saw that reason before consenting. In Sprint 114.2's adapters the only expected
irreversible step is a client CLI whose removal command does not exist; the capability matrix
currently records `SafeRemoval = supported` for all six targets, so no adapter should need one.

## 4. Consent rules

| Group | What it changes | Consent |
| --- | --- | --- |
| Agent integration (per provider) | Managed instruction block, skill files, command templates, one MCP entry in the chosen scope, local state | Interactive selection of the provider (pre-selected when detected, except generic) or `--agents`; `--yes` accepts the plan as shown; EOF is refusal |
| Managed mode | `.tracker/managed-mode.json` | Interactive mode choice or `--mode`; the recommended default is `managed` |
| Off-device backup | Backup target definition (local state), first checkpoint, remote push | Separate question with a data-boundary statement listing exactly which paths leave the machine; `--backup-target <ID>` in noninteractive mode; never implied by `--yes` alone |

Noninteractive runs fail before writing when any external-impact decision is missing. JSON mode
never prompts.

## 5. Journal, snapshots, and secrets

- The setup journal lives in the private state directory (`0700`), not in the workspace, and is
  excluded from exports, sync bundles, backups, and diagnostics like the rest of local state.
- Snapshots (`FileIdentity`) record path, existence, mode, size, and SHA-256; rollback material is
  a private copy of the whole pre-write file. Client configuration files can contain other servers'
  credentials, so rollback copies are `0600`, deleted or rotated after commit, and never included
  in any plan output, `--json` payload, log, or diagnostics bundle.
- Plan output renders `Command.Display()` (argv quoted per element) and never environment values.
- Atlas-owned entries carry no secrets by construction (`MCPRegistration` has no env; `Command`
  refuses secret-looking env names).

## 6. Crash points and expected recovery

`OperationState.RecoveryAction()` decides what a restart does with an in-flight journal entry:

| Interrupted during | Journal state | Recovery |
| --- | --- | --- |
| Before first write | `planned` | none; plan is discarded, rerun replans |
| After config snapshot, before write | `applying` (step started, no post-write identity) | roll back: restore snapshot if the file changed, else nothing |
| After instruction update | `applying` | roll back started steps in reverse |
| After MCP config update | `applying` | roll back started steps in reverse |
| After provider CLI exited | `applying` | roll back: run the recorded `run_command` rollback (for example `claude mcp remove`, `openclaw mcp unset`) |
| After all steps, before verify | `applied` | verify, then decide |
| During verify | `verifying` | verify again |
| After verify, before manifest commit | `verifying` | verify again; a passed verify then commits the manifest |
| During rollback | `rolling_back` | resume rollback; actions are idempotent |

Every recovery marks its target state first (`RecoveryTarget()`), so an interruption during
recovery is itself recoverable. These nine points are the crash-injection matrix AT114-103 must
test.

## 7. Resume and partial success

`tracker setup status` reads the manifest and the journal. A resting state per provider is
reported directly; an in-flight state is reported as "interrupted, will recover on next run" with
the recovery action, and `tracker setup repair` performs it. The combined exit status of a run is
success only when every consented transaction reached `connected` or `pending_approval`; otherwise
it is a partial-success exit with the per-provider table, and the successful providers stay
untouched.

## 8. Consequences

- Sprint 114.1 must add: setup lock, journal store, snapshot store, step executor, atomic file
  writer, and manifest store under the private state directory; the `tracker setup` command
  family; and the workspace registry / `--workspace-from-cwd --expected-workspace-id` server mode
  (AT114-102) that canonical registrations depend on.
- The existing `tracker init --integrations` interactive offer remains but is documented as the
  low-level path; AT114-106 changes the shell installer's handoff to `tracker setup`.
- No existing public interface changes in Sprint 114.0.

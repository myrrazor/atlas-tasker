# ADR: Unified Setup and Transaction Model (AT114-002)

Status: Sprint 114.0 architecture decision, revised after independent review round 1 (findings
S-A..S-D, T-A..T-C; dispositions in [release/v1.14-s0-review-round1.md](release/v1.14-s0-review-round1.md)).
Recorded as DEC-070 and revised by DEC-079 in [v1-decision-log.md](v1-decision-log.md).
Implemented by Sprint 114.1 (AT114-101..106) on top of the adapter contract in
[v1.14-provider-adapter-contract.md](v1.14-provider-adapter-contract.md) and the operation state
machine in `internal/setup/operation.go`.

## 1. Decisions

1. **`tracker init` stays low-level.** It initializes a workspace (config, identity, directories)
   and keeps its existing `--integrations` / `--skip-integrations` behavior in v1.14. It never
   registers MCP servers, never touches client configuration, never configures backup.
2. **`tracker setup` is the orchestrator.** It composes: workspace inspection, six-target
   detection, planning, consent, per-provider transactions, managed-mode policy, optional backup
   configuration, verification, and the local setup manifest. It never installs agent software and
   never initializes a directory that is not already a workspace unless the user explicitly asks
   through the existing `init` path first.
3. **Read-only plan first, always.** Every run (interactive, `--yes`, `--json`, `--plan`) begins by
   producing a complete validated `IntegrationPlan` per selected target plus the managed-mode and
   backup plans. `--plan` stops there. Nothing is written until every plan validates and consent is
   recorded; a plan that fails validation aborts the whole run before the first write.
4. **One transaction per provider.** Each provider integration is its own transaction with its
   own journal entry, snapshots, and rollback. A failure in one rolls back only that provider; the
   others keep their `connected`/`pending_*` result. Partial success is reported as such, with the
   exact per-provider state, never collapsed into a single "setup failed".
5. **Backup is a separate transaction group with separate consent.** It is planned in the same run
   but consented, applied, and reported independently (locked decision 6). A backup failure never
   rolls back agent integrations; an integration failure never prevents backup configuration.
6. **Idempotent.** Re-running setup against a workspace that already matches produces `NoOp` plans
   and writes nothing, including no journal entry and no manifest rewrite.
7. **Repair and removal reuse the adapter contract.** `Repair` and `Remove` return plans of the
   same shape (`Operation = repair | remove`) that run through the same journal. There is no second
   code path for undoing setup.
8. **No global provider state without explicit consent.** Default scopes are the project-bound
   ones in the capability matrix. Any user-level or gateway-level write (Claude `--scope user`,
   Codex `~/.codex/config.toml`, Cursor `~/.cursor/mcp.json`, Grok `~/.grok/config.toml`, OpenClaw
   gateway) requires the user to have chosen that scope explicitly in the plan. OpenClaw's only
   scope is gateway, so OpenClaw is never pre-selected by detection alone: interactively the user
   ticks it in the picker after the plan has said that its registration is machine-wide, and in
   noninteractive mode it must be named (`--agents openclaw`); `--yes` on its own never accepts a
   gateway- or user-scope write (review finding T-B).
9. **Provider trust dialogs are never bypassed.** Approval requirements become `ApprovalStep`s that
   are reported and awaited; the resulting integration state is `pending_workspace_trust` or
   `pending_mcp_approval` until `Verify` proves otherwise. Atlas never edits a client's trust or
   approval records (`~/.claude.json` project approvals, Codex `projects.<path>.trust_level`,
   Cursor enterprise allowlists, `disabledMcpjsonServers`).
10. **No agent software is installed.** Detection finds what is on the machine; a missing client
    yields a `Detection{Installed: false}` and, at most, a skill/instruction-only plan.

## 2. Operation states

`internal/setup.OperationState` is the closed set from the plan, in this order:

```text
planned  applying  applied  verifying  connected  pending_approval
failed   rolling_back  rolled_back  repair_required
```

An operation is one journal entry. Legal edges (`OperationState.Allows`, exactly seventeen, pinned
by count in `operation_test.go`):

```text
planned          -> applying
applying         -> applied | rolling_back
applied          -> verifying | rolling_back
verifying        -> connected | pending_approval | repair_required | rolling_back
connected        -> verifying | repair_required
pending_approval -> verifying | repair_required | rolling_back
failed           -> rolling_back
rolling_back     -> rolled_back | failed
rolled_back      -> (final)
repair_required  -> (final)
```

Properties the tests pin:

- Nothing reaches `applying` without `planned` (no write before a complete plan).
- Nothing reaches `connected` or `pending_approval` except through `verifying` (verification is
  never skipped, and a pending approval is re-verified rather than assumed).
- **No edge leads back to `planned`** (review finding S-A). `planned` therefore always means "this
  operation has written nothing", and `rolled_back` and `planned` are the only states with
  `MayHaveWritten() == false`. A fresh plan after `failed`, `rolled_back`, or `repair_required` is a
  *new* operation whose planning step reads the previous journal entry; it does not reuse it.
- **`failed` is reached only from `rolling_back`** (review finding S-B): an apply or verify error
  always goes through `rolling_back` first, so `failed` means "a rollback action itself failed and
  the journal lists the exact paths left for the operator", never "writes were abandoned". The
  only edge out of `failed` is another rollback attempt (`tracker setup repair`).
- `rolled_back` and `repair_required` are final (`Final()`); repair is a new operation planned from
  the journal entry.
- A journal re-mark to the same state is allowed (resume) and is not a transition.
- A plan that fails validation at apply time never leaves `planned` and, because the journal entry
  is written at step 3 of §3 only after validation, produces no journal entry at all.

The operation state is distinct from the adapter's integration state: the operation says where
the transaction is, the integration state says what it produced. `setup.OutcomeFor` is the one
mapping between the two vocabularies and is total over the nine integration states (review
finding S-C; `TestOutcomeForIsTotalOverIntegrationStates`):

| Integration state (adapter) | Operation state | Writes |
| --- | --- | --- |
| `connected`, `connected_restart_required` | `connected` | kept, verified |
| `pending_workspace_trust`, `pending_mcp_approval` | `pending_approval` | kept; a human action is outstanding |
| `configured_unverified`, `portable_ready` | `pending_approval` | kept; no verification could run (client absent, probe unavailable, portable descriptor still to be installed) |
| `unsupported_client_version` | `pending_approval` | kept; only skill/instruction files were written, no client configuration |
| `repair_required` | `repair_required` | disk and record disagree; final, repair is a new operation |
| `failed` | `rolling_back` | the engine undoes the started steps; `rolled_back` or `failed` is decided by the rollback, never by the adapter |

`pending_approval` therefore means "writes complete, correct, and kept, integration not proven
connected"; the integration state in the journal and in every report says *which* outstanding step
it is. `KeepsWrites()` (formerly `Succeeded()`, renamed because the old name read as
"connected") is true for `connected` and `pending_approval` only. A plan with no write steps (a
`NoOp`, or an unsupported client for which Atlas writes nothing) creates no operation; its
integration state is reported straight from the plan. The alternative of an eleventh operation
state (`unverified`) was considered and rejected: DEC-070 pins the ten states, and the
distinction agents need is carried by the integration state and the run-level status of §7.

## 3. Transaction protocol (per provider)

```text
1. acquire setup lock (machine-local, in the private state directory; not the workspace write lock)
2. validate every target path: inside workspace or consented root, not a symlink, parent exists
   or is creatable, no NUL, expected format parses if the file exists, owner is the current user
3. journal: planned  (plan fingerprint, target, workspace ID, step list)
4. for each step, in order:
     a. record FileIdentity{exists, mode, size, owner{uid,gid}, sha256} of the path
        (never contents into the journal)
     b. copy the pre-write file into private rollback material (0600) when the step is reversible
     c. journal: applying (step started)
     d. perform the step (atomic write: temp file + fsync + rename; or run the structured Command);
        a step inside the workspace takes the workspace write lock for its own duration only
     e. journal: step applied (post-write FileIdentity)
5. journal: applied
6. journal: verifying; run Verify
7. journal: OutcomeFor(integration state) = connected | pending_approval | repair_required
   | rolling_back
8. on connected or pending_approval: write the IntegrationState record into the local setup
   manifest (0600) and only then delete the operation's rollback material (commit)
9. release setup lock
```

**Lock ordering** (review finding T-A). The setup lock is acquired first and held for the whole
operation; the workspace write lock (`internal/service/lock.go`) is taken second, only for a step
that writes inside the workspace (`.tracker/integrations/**`, the managed instruction block, skill
files, `managed-mode.json`), and released when that step's journal record is written. The reverse
order never occurs: no code path that holds the workspace write lock may start a setup operation.
A workspace lock that cannot be acquired (the CLI's exit 6 condition) fails the step like any other
step error: the operation moves to `rolling_back`, releases the setup lock at step 9, and reports
`busy` for that provider; it does not wait holding the setup lock.

Failure at any step in 4–7 moves to `rolling_back`, runs the `Rollback` action of every started
step in reverse order (`restore_snapshot` from the private copy, `delete_created`, or the
structured `run_command` for client CLIs), and ends `rolled_back` (or `failed` when a rollback
action itself fails, in which case the journal lists the exact paths left for the operator).
Rollback material is kept until the operation ends: it is deleted at commit (step 8) or at
`rolled_back`, and retained while the operation is `failed` so a later `tracker setup repair` can
finish the rollback (review finding B-H: there is no retention window other than the operation's
own lifetime).

Irreversible steps are refused unless the plan classified them `irreversible` with a reason and
the user saw that reason before consenting. In Sprint 114.2's adapters the only expected
irreversible step is a client CLI whose removal command does not exist; the capability matrix
currently records `SafeRemoval = supported` for all six targets, so no adapter should need one.

## 4. Consent rules

| Group | What it changes | Consent |
| --- | --- | --- |
| Agent integration, project-bound scope (per provider) | Managed instruction block, skill files, command templates, one MCP entry in the target's preferred project scope, local state | Interactive selection of the provider (pre-selected when detected, except generic) or `--agents`; `--yes` accepts the plan as shown; EOF is refusal |
| Agent integration, machine-wide scope (OpenClaw gateway; any `user` scope) | The same, but the MCP entry is visible to every project on the machine | Never pre-selected. Interactively the provider or scope must be ticked after the plan has shown the machine-wide effect; noninteractively it must be named (`--agents openclaw`, `--scope user`); `--yes` alone is not consent |
| Managed mode | `.tracker/managed-mode.json` | Interactive mode choice or `--mode`; the recommended default is `managed`; `delivery` is refused here (it is a separate power-user action, see the managed-mode contract) |
| Off-device backup | Backup target definition (local state), first checkpoint, remote push | Separate question with a data-boundary statement listing exactly which paths leave the machine; `--backup-target <ID>` in noninteractive mode; never implied by `--yes` alone |

Noninteractive runs fail before writing when any external-impact decision is missing. JSON mode
never prompts.

## 5. Journal, snapshots, and secrets

- The setup journal lives in the private state directory (`0700`), not in the workspace, and is
  excluded from exports, sync bundles, backups, and diagnostics like the rest of local state.
- Snapshots (`adapter.FileIdentity`) record path, existence, mode, size, owner (`uid`/`gid`), and
  SHA-256, which is the "file identity, mode, ownership, and SHA-256" AT114-103 step 3 requires; a
  file whose owner is not the current user is refused at step 2, and an owner change between
  snapshot and rollback is drift (`repair_required`), never silently overwritten. Rollback material
  is a private copy of the whole pre-write file. Client configuration files can contain other
  servers' credentials, so rollback copies are `0600`, deleted at commit or at `rolled_back`
  (retained only while an operation is `failed`), and never included in any plan output, `--json`
  payload, log, or diagnostics bundle.
- Plan output renders `Command.Display()` (argv quoted per element) and never environment values.
- Atlas-owned entries carry no secrets by construction (`MCPRegistration` has no env; `Command`
  refuses secret-looking env names).

## 6. Crash points and expected recovery

`OperationState.RecoveryAction()` decides what a restart does with an in-flight journal entry:

| Interrupted during | Journal state | Recovery |
| --- | --- | --- |
| Before first write | `planned` | none; plan is discarded, rerun replans |
| After config snapshot, before write | `applying` (step started, no post-write identity) | roll back: restore snapshot if the file changed, else nothing |
| After instruction update | `applying` | roll back started steps in reverse |
| After MCP config update | `applying` | roll back started steps in reverse |
| After provider CLI exited | `applying` | roll back: run the recorded `run_command` rollback (for example `claude mcp remove`, `openclaw mcp unset`) |
| After all steps, before verify | `applied` | verify, then decide |
| During verify | `verifying` | verify again |
| After verify, before manifest commit | `verifying` | verify again; a passed verify then commits the manifest |
| During rollback | `rolling_back` | resume rollback; each action kind recognises work the crash already finished (below) |

Every recovery marks its target state first (`RecoveryTarget()`), so an interruption during
recovery is itself recoverable. These nine points are the crash-injection matrix AT114-103 must
test.

**Rollback idempotency, per action kind** (review finding S-D; implemented and table-tested in
AT114-103 by resuming each action twice). "Idempotent" is not assumed of any client CLI; it is
constructed by the engine:

| Rollback kind | Before acting | Already-done condition (success without acting) | Real failure |
| --- | --- | --- | --- |
| `restore_snapshot` | compare the current `FileIdentity` with the step's post-write identity and with the snapshot | current identity equals the snapshot (owner, mode, size, SHA-256) | current identity matches neither: the file changed after Atlas wrote it, so the engine stops, marks `failed`, and lists the path instead of overwriting a third party's edit |
| `delete_created` | `lstat` the path | `ENOENT` | the path exists but its identity is not the post-write identity (someone replaced it): stop and list, as above |
| `run_command` (`remove`) | run the provider's read-only listing probe from the capability matrix (`claude mcp get`, `codex mcp get`, `openclaw mcp show --json`, `grok mcp list --json`) with the same detected executable | the entry is absent, or the removal command exits with the adapter's documented "not found" classification when no probe is available | any other non-zero exit; `openclaw mcp unset` and (until AT114-204 proves otherwise) `claude mcp remove` are assumed to fail on an absent name, so the probe is mandatory for them |
| `run_command` (`reload`) | none | always re-runnable | non-zero exit |

Only rollback actions recorded in the journal as *started* are resumed; an action the journal
recorded as *done* is not re-run. The engine never proceeds past a real failure to earlier steps'
snapshots without recording it: it continues the reverse walk, restores what it can, and ends
`failed` with the complete list of paths left behind.

## 7. Resume and partial success

`tracker setup status` reads the manifest and the journal. A resting state per provider is
reported directly; an in-flight state is reported as "interrupted, will recover on next run" with
the recovery action, and `tracker setup repair` performs it.

**Run-level status** (review findings S-C and T-C). Agents branch on the top-level status and the
exit code, so "connected" and "awaiting a human" are never merged. Every `tracker setup` and
`tracker setup status` report carries, per provider, both the operation state and the integration
state, and one run-level `status` derived from them:

| Run-level `status` | Condition | Exit |
| --- | --- | --- |
| `connected` | every consented operation is `connected` | 0 |
| `pending` | every consented operation keeps its writes (`KeepsWrites()`) and at least one integration state is `pending_workspace_trust` or `pending_mcp_approval` | 0 |
| `unverified` | every consented operation keeps its writes, none is awaiting a human, and at least one integration state is `configured_unverified`, `portable_ready`, or `unsupported_client_version` | 0 |
| `partial` | at least one operation keeps its writes and at least one ended `rolled_back`, `failed`, or `repair_required` | non-zero |
| `failed` | no consented operation keeps its writes | non-zero |

The three exit-0 statuses are distinct strings so an agent that needs a proven connection checks
`status == "connected"` rather than the exit code; the exact non-zero codes for `partial` and
`failed` are fixed by AT114-104 within the existing exit-code table. The successful providers of a
`partial` run stay untouched.

## 8. Consequences

- Sprint 114.1 must add: setup lock, journal store, snapshot store, step executor, atomic file
  writer, and manifest store under the private state directory; the `tracker setup` command
  family; and the workspace registry / `--workspace-from-cwd --expected-workspace-id` server mode
  (AT114-102) that canonical registrations depend on. AT114-103 additionally owns the per-kind
  rollback idempotency table of §6, the lock ordering of §3, and the owner check in `FileIdentity`;
  AT114-104 owns the run-level status vocabulary of §7 and the noninteractive naming rule for
  machine-wide scopes of §4.
- The existing `tracker init --integrations` interactive offer remains but is documented as the
  low-level path; AT114-106 changes the shell installer's handoff to `tracker setup`.
- No existing public interface changes in Sprint 114.0.

# v1.9 Agent Workflow

v1.9 adds a narrow coordination layer for coding agents. Atlas still does not host agents or run a scheduler by default; it exposes clearer work queues and event-driven wake-up records.

## Agent Work Queues

Use these reads first:

```bash
tracker agent available <agent-id> --json
tracker agent pending <agent-id> --json
```

`available` lists work the agent can act on now, including `promote` entries for backlog tickets whose blockers are all `done` (the first suggested command is the `ticket move <ID> ready`). `pending` lists relevant work that is blocked or waiting, with reason codes such as `dependency_blocked`, `waiting_for_review`, `claimed_by_other`, `policy_blocked`, and `agent_at_capacity`.

## Wake-Ups

When a ticket reaches `done`, Atlas checks tickets blocked by that ticket. If an assigned agent ticket is now unblocked, Atlas promotes it from `backlog` to `ready` (a `ticket.moved` by `agent:atlas`, reason `unblocked: <BLOCKER> completed by <ACTOR>`, chained to the completion by correlation and causation ids), records an `agent.work_available` event, and writes a local wake-up record:

```bash
tracker agent wakeups list <agent-id> --json
tracker agent wakeups view <wakeup-id> --json
tracker agent wakeups ack <wakeup-id> --actor agent:<agent-id> --reason "picked up"
```

Wake-up records are local runtime records under `.tracker/runtime/agent-wakeups/`. The matching `agent.work_available` event is recorded with the reserved system actor `agent:atlas`.

The promotion is best-effort. If it fails, the blocker completion still succeeds and the wake-up lands anyway with `metadata.promoted` set to `"false"` and `metadata.promotion_error` saying why (a move that died after its canonical write is left in the mutation journal, the wake-up is recorded as `failed`, and its error points at `tracker doctor --repair`, which replays the move); a successful one carries `metadata.promoted = "true"` and the reason `dependency completed; ticket promoted to ready`. A ticket someone set to `blocked` by hand is woken but never moved. Dependents assigned to a human, or to nobody, are not promoted at all; they surface under `unblocked_for_me` in `tracker queue` and `tracker next` instead.

Only `done` unblocks dependencies. `canceled` does not. `human:owner` can intentionally override unresolved dependencies with `--override-deps --reason <TEXT>` on unsafe ticket progress commands; Atlas records the unresolved blockers in the mutation history.

## Auto Mode

Default mode is notify-only:

```bash
tracker agent auto status <agent-id>
```

Owners can enable command mode with argv items:

```bash
tracker agent auto set <agent-id> \
  --mode command \
  --argv /absolute/path/to/agent-runner \
  --argv "{ticket_id}" \
  --argv "{wakeup_id}" \
  --actor human:owner \
  --reason "enable local wake-up runner"
```

Atlas never stores shell strings for command mode. Direct shell interpreters such as `sh`, `bash`, `zsh`, `fish`, `cmd`, `powershell`, and `pwsh` are rejected.

## Surface Parity

| Capability | CLI | Slash shell | TUI | MCP |
|---|---:|---:|---:|---:|
| Agent available work | yes | yes | Queues tab | `atlas.agent.available` |
| Agent pending work | yes | yes | Queues tab | `atlas.agent.pending` |
| Wake-up list/view/ack | yes | yes | Ops tab list | deferred |
| Agent auto status/set/off | yes | yes | Ops tab status only | deferred |
| Skill pack install | yes | yes | no | no |

Slash shell parity comes from the CLI parser. The new v1.9 queue surface is MCP read-only; existing workflow-profile MCP tools still use the same service rules as the CLI, including request-review reviewer assignment and owner-only dependency override.

Known v1.10 wake-up follow-ups are tracked in [Known Limitations](KNOWN_LIMITATIONS.md).

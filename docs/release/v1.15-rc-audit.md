# v1.15 RC audit resolution

The independent Grok Build evaluation used main at `28c035d`. The follow-up was
implemented with terminal Grok Build 4.6 at xhigh effort and reviewed by Codex.
The software release remains separate from merging this source update.

| Finding | Resolution |
| --- | --- |
| P1: default MCP profile was read | CLI `mcp serve`, `tools`, and `schema` default to workflow. Explicit `read` and `--read-only` remain read-only; the Go library default is unchanged. |
| P2: init detects Grok but cannot register it | Production registration now falls back to the same executable lookup used for detection. Injected test lookups still work. |
| P3: assigned backlog missing from queue/next | An `assigned_backlog` category follows ready and unblocked work. It shows `not_ready_status` without changing status or claiming work. Other actors’ and unassigned ordinary backlog are excluded. |
| P4: high-impact approvals | Retained. The danger flag, external one-time approval, actor/reason, and service permissions serve different checks. |
| P5: bootstrap creates no project | Explicit `--init-if-missing` creates a first project and registers with Home. Existing empty workspaces are repaired without rewriting config or identity. Machine opt-outs remain respected. Actor and ticket type stay explicit; ordinary CLI ticket creation does not require a reason. |
| N1: Grok receives no MCP tools | Grok-compatible underscore names are registered automatically. A real Grok 4.6 xhigh session loaded 94 tools and answered a plain project-status question through Atlas MCP. Client trust and restart prompts remain controlled by Grok. |
| N2: Home reports a successful project setup as unverified | Home distinguishes user and project Grok entries and displays their actual command and config location. Unrelated user configuration produces no false Atlas row. A matching file is configured/pending restart; only a successful tool call proves a live connection. |
| N3: board/project list outside a workspace | Workspace reads stay explicitly scoped. Errors point to Home and workspace grants. Home lists registered workspaces and discovery stays inside granted roots; Atlas does not crawl the whole home directory. |
| N4: JSON/no-open omits claim URL | Retained. Claim tokens are browser sign-in secrets, excluded from machine output. Agents use CLI/MCP for tickets. |
| N5: unreadable long default keys | Existing valid short names are preserved. Long multiword names use the first valid short word, otherwise `MAIN`; existing projects are not renamed. |
| N6: source/go-install cannot uninstall | Successful init/setup records a verified running Atlas executable, on-disk identity, and hash when ownership permits. Uninstall remains receipt-bound; modified binaries are refused and other installation receipts are preserved. No force-delete option was added. |
| N7: curl installs the last release | Retained. The installer fetches published, verifiable release assets. README and website label v1.15 as a source preview until release publication. |
| N8: portable paths are partial | Grok project config uses bare `tracker` only when PATH resolves to the intended executable. An allowed absolute fallback stays launchable. A home-local source binary missing from PATH gets guidance to fix PATH; project configuration never embeds a prohibited personal home path. User-level entries may use absolute commands. |
| N9: Home requires a one-time claim | Retained. One claim establishes the essential local browser session; no nonessential cookies or cookie banner were added. |
| N10: nested help is unknown | `tracker ticket help`, `mcp help`, `agent help`, and other common parent commands work outside a workspace. Unknown targets still fail with exit 2. |

The README and marketing pages include current dark product captures and the real
Grok status session. Terminal/TUI output remains a polished table by default;
browser boards remain Kanban. The favicon is extracted from the existing Atlas A.

The follow-up also includes a real 50-second Grok Build video: an eight-ticket
status read, an MCP ticket creation, and the refreshed nine-ticket board. It uses
synthetic data, with pauses shortened and local client chrome cropped. The README
and website link a text transcript and retain the source-preview notice.

See [DEC-106–110](../v1-decision-log.md#dec-106--simple-install-init-restart-then-ask),
[release evidence](v1.15.0-release-evidence.md), and `TEST_STDOUT.log` for the
implementation decisions and validation record. A successful local fixture is not
an off-device disaster drill or proof that every supported coding client is connected.

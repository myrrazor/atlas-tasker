## Sprint 114.2 — all six agent integrations

### AT114-201 — Canonical Atlas MCP registration specification

**Implementation**

Define one provider-neutral model:

```json
{
  "server_name": "atlas-workspace_ab12cd",
  "transport": "stdio",
  "command": "/verified/path/tracker",
  "args": [
    "mcp",
    "serve",
    "--workspace",
    "/verified/workspace",
    "--tool-profile",
    "workflow",
    "--max-items",
    "30",
    "--max-result-bytes",
    "65536"
  ],
  "actor_hint": "agent:builder-1"
}
```

Requirements:

- Server name derived from workspace ID, not project name.
- No secrets in command, args, or environment.
- Absolute executable validated before registration.
- Workspace bound by absolute path or verified cwd plus expected ID.
- Workflow profile only.
- Result bounds fixed.
- Stdio only for the local integration.
- High-impact tools absent.

**Verification**

Start the exact configured server command directly and perform:

- MCP initialize.
- Tool listing.
- `atlas.dashboard`.
- `atlas.board`.
- One permitted workflow mutation in a temporary workspace.
- High-impact tool absence.
- Clean shutdown.

### AT114-202 — Integrate MCP registration with the existing skill installer

**Implementation**

Refactor the existing integration flow so one provider setup operation performs:

- Refresh provider-specific managed block.
- Refresh the existing atlas-worker skill.
- Refresh command templates.
- Register MCP.
- Record actor mapping.
- Verify both layers.

Do not create an `atlas-manager`, `atlas-board`, or second skill.

The skill must contain a small generated provider/actor context without exposing machine-specific
secrets.

**Acceptance**

- Existing custom content remains unchanged.
- Codex, Cursor, OpenClaw, and Grok managed blocks continue coexisting in `AGENTS.md`.
- Claude remains in `CLAUDE.md`.
- Reinstallation updates only Atlas-owned content.
- Skill and MCP versions cannot drift silently.

### AT114-203 — Codex adapter

**Implementation**

Preferred scope: `.codex/config.toml`

Use a managed `[mcp_servers.<name>]` section.

Configure:

- Trusted absolute command.
- Workspace binding.
- `required = false`; a broken optional Atlas server must not prevent all Codex use.
- A write-aware tool-approval posture where supported.
- Workflow-only server profile.

Codex officially supports project-scoped `.codex/config.toml`, shares MCP configuration across
local Codex surfaces on the same host, and provides `codex mcp list` for inspection. (Verified;
see the capability matrix for the trust requirement and the CLI's user-scope-only write behavior.)

**Verification**

- Parse resulting TOML.
- Preserve unrelated TOML tables and comments where feasible.
- Run `codex mcp list`.
- Run direct MCP self-probe.
- Start a real Codex session in a temporary workspace.
- Ask for Atlas status.
- Confirm Codex calls `atlas.status` or `atlas.dashboard`.
- Confirm normal workflow tool succeeds.
- Confirm high-impact tools are unavailable.
- Test restart-required state where applicable.

**Negative tests**

- Existing unmanaged same-name server.
- Malformed TOML.
- Symlinked config.
- Wrong workspace.
- Wrong binary.
- Unsupported Codex version.
- Config changed after planning.

### AT114-204 — Claude Code adapter

**Implementation**

Prefer Claude's local project scope for machine-local seamless setup. Support project `.mcp.json`
as an explicit shared option.

Use:

```text
claude mcp add ...
claude mcp get ...
claude mcp list
```

Claude distinguishes local, project, and user scopes; project `.mcp.json` entries can require
workspace trust or explicit approval, which setup must report rather than bypass. (Verified.)

**Verification**

- Skill in `.claude/skills/atlas-worker`.
- Commands remain in `.claude/commands`.
- MCP entry targets the correct workspace.
- `claude mcp get` reports expected command and args.
- Status distinguishes connected from pending approval.
- Real Claude Code prompt retrieves board state.
- Workflow mutation carries configured actor.
- Removal preserves unrelated Claude settings.

**Negative tests**

- Rejected project MCP.
- Disabled project MCP.
- Workspace trust pending.
- Existing same-name server at a higher-precedence scope.
- User config changed between plan and apply.
- Malformed `.mcp.json`.

### AT114-205 — Cursor adapter

**Implementation**

Manage: `.cursor/mcp.json`

Use `${workspaceFolder}` where appropriate so repository-carried config does not embed a user's
home path.

Cursor officially supports project-specific `.cursor/mcp.json`, local stdio servers, MCP Apps, and
structured tool responses. (Verified.)

**Verification**

- Merge only the Atlas `mcpServers` entry.
- Preserve unrelated entries and formatting where possible.
- Validate JSON before replacement.
- Directly probe the configured Atlas command.
- Confirm Cursor lists the Atlas tools.
- Ask Cursor for project status.
- Confirm read tool use.
- Confirm one workflow action.
- Confirm optional board MCP App and Markdown fallback.

**Negative tests**

- Existing same-name unmanaged server.
- JSON with duplicate keys.
- Symlinked `.cursor`.
- Workspace-folder substitution resolving outside the Atlas workspace.
- Enterprise MCP policy blocking the server.
- Cursor restart required.

### AT114-206 — OpenClaw adapter

**Implementation**

Use the supported CLI registration flow:

```text
openclaw mcp add <workspace-specific-name>
openclaw mcp doctor <name> --probe
```

OpenClaw stores configured servers through its Gateway and explicitly distinguishes saved
configuration from a successful live probe. (Verified.)

Because the definition is not purely project-local, use a workspace-ID-derived name and a fixed
canonical `--cwd`.

**Verification**

- Existing repo-local `.agents/skills/atlas-worker` remains.
- Optional current `--global` skill behavior remains separately consented.
- MCP server name cannot collide across workspaces.
- `openclaw mcp doctor --probe` succeeds.
- A real OpenClaw session returns Atlas status.
- Removal removes only the exact Atlas-owned server.
- Gateway reload/restart requirement is reported.

**Negative tests**

- Gateway unavailable.
- Existing name collision.
- Wrong cwd.
- Probe failure.
- Config saved but server unreachable.
- OpenClaw changed entry after Atlas setup.
- Global skill and MCP removal operate independently.

### AT114-207 — Grok Build adapter

**Implementation**

Use native project scope:

```text
grok mcp add --scope project ...
grok mcp list --json
grok mcp doctor <name> --json
```

Grok Build supports local stdio MCP servers, project scope through `.grok/config.toml`, JSON
diagnostics, and compatibility imports from some other client configurations. (Verified.)

**Verification**

- Native Grok entry takes deterministic precedence over compatibility-imported Atlas entries.
- No duplicate Atlas tool catalog.
- Existing `.grok/config.toml` content preserved.
- `grok inspect` attributes the server to the intended source.
- `grok mcp doctor` succeeds.
- Real Grok prompt returns current board state.
- One workflow mutation succeeds.
- High-impact operations remain absent.

**Negative tests**

- Duplicate server through `.mcp.json` or Cursor compatibility import.
- Unsupported Grok version.
- Malformed TOML.
- Wrong project root.
- Native/compatibility precedence changes.
- Doctor reports configured but unreachable.

### AT114-208 — Generic agent adapter

**Implementation**

Generic support contains:

- Existing generic `AGENTS.md` managed block.
- Existing generic skill.
- Portable MCP JSON descriptor.
- Optional root `.mcp.json` managed entry.
- Optional user-supplied config destination selected through setup.
- Direct Atlas MCP self-probe.
- A small conformance host used in tests.

States:

```text
portable_ready
connected_by_standard_config
connected_by_custom_adapter
configured_unverified
```

Do not claim a universal unknown client is connected merely because a file exists.

**Acceptance**

- Generic receives the same workflow profile.
- Portable descriptor contains no absolute secret-bearing path.
- Custom config path must pass containment, owner, symlink, and format validation.
- Removal preserves unrelated entries.
- Generic conformance host discovers and invokes Atlas tools.

### AT114-209 — Agent identity, team policy, and cross-provider collision handling

**Implementation**

Setup maps each selected provider to an Atlas agent identity.

Rules:

- Reuse compatible existing agents when explicitly selected.
- Never overwrite existing role or permission assignments silently.
- One-agent setup may suggest the existing `solo` preset.
- Multi-agent setup may suggest `pair`, `swarm`, or `crossfire`.
- Provider and Atlas actor are distinct concepts.
- Every MCP write still receives an explicit actor and reason.
- Actor hints guide the skill; they do not bypass server authorization.

Test all-provider coexistence:

- Codex, Cursor, OpenClaw, Grok blocks in one `AGENTS.md`.
- Claude in `CLAUDE.md`.
- Generic block coexists.
- Native Grok config does not duplicate imported Atlas config.
- All server names resolve to the same workspace but retain distinct provider identity.
- Review separation remains effective.

# Atlas Tasker v1.15

This candidate combines the unmerged v1.14 implementation with Atlas Home, simpler setup, a polished terminal table, and software-only uninstall. Publication and deployment remain separate from submitting the implementation for review.

## Baseline and delivery

The integration starts at `main` commit `b95fd640c5b6bd956aadf5ac08d4b5b460e33de2` and incorporates the compatible v1.14 stack through `d2ad0a4abd2e47e4e7d9917edf81bc4ca31f04a4` (PRs #145–154). The earlier `feat/scheduled-tickets-ui` work at `9c82db39cb6220eb4139299ad9c08fc0448255a2` is already an ancestor of main. It is not the newest feature baseline.

For this candidate, feature pull requests target `main` directly after local verification. The owner explicitly selected this delivery path in place of the previous dev/testing promotion sequence. Nothing in this document authorizes merging, tagging, publishing a binary, or deploying the website.

## Implementation contract

| Area | Result required for v1.15 |
| --- | --- |
| First use | `tracker init` initializes and registers a workspace, creates its first project when needed, configures supported agents, enables local checkpoints, and makes Home available. Repeating it preserves identity, custom content, and opt-outs. |
| Home | Bare `tracker` reaches one user-level loopback service from any directory. It verifies service identity on the configured port and refuses a foreign listener. |
| Workspaces | The registry holds pointers and health metadata. Discovery stays within approved roots; move, copy, fork, hide, and remove-pointer operations preserve canonical data. |
| Browser | Home, attention, search, settings, workspace projects, activity, and backup lead into the existing Kanban and ticket workflow. Browser mutations retain origin/session/CSRF checks and revision preconditions. |
| Terminal | A polished table is the default in terminal and TUI output. Color supplements status labels. Optional Kanban cards remain available; long lists and narrow screens retain access to every ticket. |
| Agents | One global workflow MCP registration per supported client, explicit workspace scope for cross-workspace writes, registered tools/resources, native Markdown, and an optional read-only MCP App board. |
| Recovery | Canonical-only checkpoints use an isolated bare Git repository. Remote publication needs an explicit target and independent fetch/hash verification. Restore applies the exact approved plan to a clean destination. |
| Uninstall | Preview and remove only verified Atlas software, units, and managed integration entries. Preserve projects, tickets, events, registry pointers, backups, and recovery material. |
| Documentation | README, software docs, migration instructions, website, and site docs describe the same current behavior. Favicon, sitemap, robots.txt, page metadata, social preview, and custom 404 work locally. No nonessential cookies or cookie banner. |

The prior v1.14 setup, governance, actor separation, redaction, managed integration, backup, and recovery contracts continue to apply except where an explicitly linked v1.15 decision supersedes a default. Canonical Markdown and events remain authoritative; indexes and global summaries are rebuildable.

## Evidence boundaries

Required local evidence includes the complete Go tests and vet, race/fuzz lane, installer and MCP subprocess harnesses, browser/site contracts, security tooling, and visual checks of the rendered product. `TEST_STDOUT.log` records the final required local suite. Targeted fixtures exercise repeat setup, multiple workspaces, path/identity conflicts, stale revisions, concentrated ticket lists, backup isolation, restore binding, and data-preserving uninstall.

Local fixture remotes prove the Git protocol and integrity checks; they do not prove an off-device disaster drill. Tests with injected provider commands do not prove that every installed client has restarted or connected. This PR does not claim a hosted deployment or published v1.15 release.

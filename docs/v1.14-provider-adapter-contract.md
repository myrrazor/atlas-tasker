# v1.14 Provider Adapter Contract and Capability Matrix (AT114-003)

Status: Sprint 114.0 contract artifact, revised after independent review round 1 (dispositions in
[release/v1.14-s0-review-round1.md](release/v1.14-s0-review-round1.md)). The Go contract lives
in `internal/integrations/adapter`; this document explains it, records the verified provider
facts behind the capability matrix, and lists what remains unverified until Sprint 114.2 runs real
clients. No provider adapter is implemented yet; Sprint 114.2 (AT114-203..208) implements one
adapter per target against this contract without changing it.

Related: [v1.14 implementation plan](v1.14-implementation-plan.md) (AT114-003, AT114-201,
AT114-208, locked decisions 2–5), [unified setup ADR](v1.14-setup-transaction-model.md),
decision log entries DEC-071, DEC-072, DEC-076, DEC-077, and DEC-078 in
[v1-decision-log.md](v1-decision-log.md).

## 1. Scope and non-goals

The contract fixes:

- one interface every target implements (`AgentIntegrationAdapter`);
- the nine reportable integration states from locked decision 5;
- the canonical Atlas MCP registration (locked decision 3, AT114-201) and how it is bound to one
  workspace (locked decision 4);
- a structured command model that makes shell interpolation impossible;
- a plan/apply/verify/repair/remove data model with fail-closed validation;
- the six-target capability matrix with the official source of every claim.

It does not implement detection, file editing, TOML/JSON merging, client CLI execution, the
setup journal, or the workspace registry. Those are Sprint 114.1 and 114.2 tickets.

## 2. Interface

```go
type AgentIntegrationAdapter interface {
    Target() integrations.Target
    Capabilities() Capabilities
    Detect(ctx context.Context, input DetectInput) Detection
    Plan(ctx context.Context, input PlanInput) (IntegrationPlan, error)
    Apply(ctx context.Context, plan IntegrationPlan) (ApplyResult, error)
    Verify(ctx context.Context, state IntegrationState) (Verification, error)
    Repair(ctx context.Context, state IntegrationState) (RepairPlan, error)
    Remove(ctx context.Context, state IntegrationState) (RemovalPlan, error)
}
```

`Target()` and `Capabilities()` are additions to the plan's six-method sketch. They let the
setup engine and the `Registry` check an adapter against the frozen matrix instead of trusting
it: `Registry.Register` rejects an adapter whose target is unknown, duplicated, or whose
`Capabilities()` differ from the matrix row in any field (the comparison is over the canonical JSON
of the whole struct, so a widened scope list, a changed binding, a dropped approval requirement,
or a different source URL is refused, not only a changed cap or preferred scope).

Method contract:

| Method | Writes | Runs client binary | Returns |
| --- | --- | --- | --- |
| `Detect` | never | only through `DetectInput.Runner`, only `detect_version`/`inspect` purposes, only the executable the detection itself reports | `Detection` (validated: installed ⇒ absolute executable; `supported` ⇒ parsed version; probes read-only and run `ExecutablePath`) |
| `Plan` | never | never | `IntegrationPlan` with `Operation = setup` |
| `Apply` | only the plan's steps, in order, under the setup journal | only `Command` values carried by plan steps, all of which run `Detection.ExecutablePath` | `ApplyResult`; may report `pending_*`, `configured_unverified`, `portable_ready`, or `failed`, never `connected` |
| `Verify` | never | read-only probes: client probes run the detected client executable, `probe` runs the registered server executable | `Verification`; the only method allowed to produce `connected` / `connected_restart_required` |
| `Repair` | never | never | `RepairPlan` (`Operation = repair`) |
| `Remove` | never | never | `RemovalPlan` (`Operation = remove`) |

Only `Apply` mutates, and only what a validated plan says. This is what makes the AT114-002
transaction model enforceable: the engine snapshots each `PlanStep.Path` before `Apply`, runs
the step, and uses the step's `Rollback` on failure.

## 3. State vocabulary

`adapter.State` is exactly the nine strings of locked decision 5:

| State | Meaning | `Verified()` | `RequiresHumanAction()` |
| --- | --- | --- | --- |
| `connected` | Registration proven by a passed probe or client-native check | yes | no |
| `connected_restart_required` | Proven, but the client process must restart/reload before it sees the server | yes | yes |
| `pending_workspace_trust` | Config is in place; the client's workspace trust dialog is outstanding | no | yes |
| `pending_mcp_approval` | Config is in place; the client's per-server approval or admin policy is outstanding | no | yes |
| `configured_unverified` | Config is in place; no verification method could run (client absent, probe unavailable) | no | no |
| `portable_ready` | A portable descriptor and skill exist; no client is bound | no | no |
| `unsupported_client_version` | Client found but version unknown/unsupported; Atlas wrote no client configuration | no | yes |
| `repair_required` | Recorded state and disk disagree (moved workspace, changed entry, stale skill) | no | yes |
| `failed` | Apply or verify failed; rolled back | no | yes |

Rules enforced by `Validate()` on the plan and result types:

- `Apply` can never return a verified state; only `Verify` can (`ApplyResult.Validate`).
- A verified `Verification` needs at least one passed check whose method is not
  `manual_client_check`, plus a `ConnectionKind` whose target class matches (generic ⇔
  `standard_config`/`custom_adapter`) and that is backed by a passed check of one of its own
  methods: `client_native` by `client_cli_list`/`client_cli_get`/`client_cli_doctor`, `self_probe`
  by `self_probe`, the two generic kinds by `conformance_host`. Every probe record must be read-only
  and must run either the detected `ClientExecutable` or, for `probe`, the registered
  `ServerExecutable`.
- A plan with `ApprovalSteps` must promise exactly the pending state those steps imply
  (`pending_workspace_trust` when any step is trust-gated, otherwise `pending_mcp_approval`), and a
  plan may promise a pending state only when it carries the approval step that names the human
  action; a plan for an unsupported version may only end in `unsupported_client_version` and may not
  carry client-config steps; a plan for an uninstalled client may not end verified.
- Each target has a `MaxPlannedState` (`stateAtMost`): generic caps at `portable_ready`, OpenClaw at
  `connected_restart_required`, the other four at `connected`. The ranks are strict: `connected` (5)
  outranks `connected_restart_required` (4), which outranks `configured_unverified` and
  `portable_ready` (2); every other state ranks 0. An OpenClaw plan therefore cannot promise
  `connected`.

**Promised state versus verified state.** `MaxPlannedState` bounds what a *plan* may promise before
anything runs. It does not bound `Verification`: when a post-apply probe proves the registration
(for OpenClaw, `openclaw mcp doctor --probe` opens a live session), `Verify` reports `connected`
with the evidence that proved it. The cap is a claim limit, not a ceiling on observed truth; the
reviewer's suggestion to clamp `Verification.State` to the cap was rejected for that reason
(DEC-078).

### 3.1 AT114-208 state names

AT114-208 lists `connected_by_standard_config` and `connected_by_custom_adapter` for the generic
target while locked decision 5 fixes nine states. The contract keeps the nine states and models
the AT114-208 distinction as `Verification.ConnectionKind`:

| `ConnectionKind` | Used by |
| --- | --- |
| `client_native` | Codex, Claude Code, OpenClaw, Grok when the client's own CLI proved the server |
| `self_probe` | Any named client verified only by Atlas starting the exact registered command |
| `standard_config` | Generic, after a managed `.mcp.json` entry passed the conformance host |
| `custom_adapter` | Generic, after a user-selected config destination passed the conformance host |

`Verification.Validate` requires a generic verified result to carry `standard_config` or
`custom_adapter`. This is recorded as DEC-071 and flagged for design review; if review prefers
eleven states, only `state.go`, this section, and the plan text change.

## 4. Canonical registration (AT114-201, locked decisions 3 and 4)

`MCPRegistration` is provider-neutral. Adapters render it into their client's native form; they
never assemble argv by hand.

```text
server_name   atlas-<first 12 hex of sha256(workspace UUID)>      pattern ^atlas-[0-9a-f]{12}$
transport     stdio
command       absolute tracker path | "tracker" (portable only)
args          mcp serve <binding> --expected-workspace-id <UUID>
              --tool-profile workflow --max-items 30 --max-result-bytes 65536
actor_hint    optional contracts.Actor (agent:<id>)
```

`RegistrationArgs` is the single derivation; `MCPRegistration.Validate` rejects any `Args` that
differ from it, any occurrence of `--dangerously-allow-high-impact-tools`, `--init-if-missing`,
or `--read-only`, any profile other than `workflow`, and any bounds other than 30 / 65536.

### 4.1 Workspace binding

| `WorkspaceBinding.Kind` | argv | Allowed scopes | Rationale |
| --- | --- | --- | --- |
| `absolute_path` | `--workspace /canonical/root` | `project_local`, `user`, `gateway` (machine-local files only) | Plan AT114-102: "use absolute --workspace where the provider supports a reliable local-project registration" |
| `client_variable` | `--workspace ${workspaceFolder}` (Cursor `.cursor/mcp.json` only) | `project_shared` | The client expands the variable before spawning the server; the server still checks the expected ID |
| `verified_cwd` | `--workspace-from-cwd` | `project_shared` (`.codex/config.toml`, `.grok/config.toml`, Claude and generic `.mcp.json`, portable descriptor) | Repository-carried files must not embed a machine path; the server resolves the workspace from the directory the client starts it in |

Every binding carries `--expected-workspace-id <UUID>`. This is stronger than the plan's minimum
("absolute path **or** verified cwd plus expected ID") on purpose: a moved, copied, or replaced
workspace at a still-valid absolute path must fail closed rather than answer for the wrong data.
`--workspace-from-cwd` and `--expected-workspace-id` do not exist in v1.13.0's `tracker mcp serve`;
AT114-102 adds them with the security rules listed in the plan. Until then a canonical
registration cannot be started by the real binary, which is why Sprint 114.2 depends on AT114-102.

**Placeholders.** A `client_variable` binding accepts exactly one bare `${name}` placeholder
(`^\$\{[A-Za-z][A-Za-z0-9_]*\}$`). Shell-style defaults such as `${CLAUDE_PROJECT_DIR:-.}` are
refused: a client that does not expand the variable passes the literal string, and a default of
`.` would silently bind the server to whatever directory it happened to start in. Review round 1
(finding G) established from the official Claude Code documentation that `CLAUDE_PROJECT_DIR` is
set in the *spawned server's environment* and is not expanded by Claude Code inside a project
`.mcp.json`, so the previous Claude `client_variable` row would have produced exactly that failure.
Claude's `.mcp.json` row is therefore `verified_cwd` (DEC-076). Only Cursor documents variable
interpolation in its project file, so only Cursor may use `client_variable` in a repository-carried
scope (`TestMatrixInvariants`).

`ValidateForScope(scope, home)` adds the repository-carried rules: a `project_shared`
registration may not use `absolute_path` and may not name an executable under the user's home
directory unless it is the portable bare `tracker`. When `home` is known the check is exact; when
it is empty the conventional per-user roots `/home/`, `/Users/`, and `/root/` are refused
heuristically, so an unknown home can never let a personal path into a committed file. Portable
registrations must use `verified_cwd`.

`RequiresDir()` is true for `verified_cwd` and `client_variable` registrations; `ServeCommand`
refuses to build a self-probe for them without an explicit working directory, and for
`client_variable` it substitutes that directory for the placeholder because Atlas, not the
client, spawns the probe.

**AT114-201 trade-off.** The plan asks for an absolute tracker path in the registration. In a
repository-carried file that conflicts with the storage rule "no machine-specific absolute
paths", so the contract allows `/usr/local/bin/tracker`-style system paths (identical across
machines that installed through the installer) and refuses per-user paths; a per-user install must
use `project_local`/`user` scope or the portable bare `tracker`. AT114-102 owns the remaining
decision of how the server learns its start directory (the plan may treat the server-environment
`CLAUDE_PROJECT_DIR` as corroborating evidence, never as the binding).

### 4.2 Rendered forms

`StandardConfigJSON()` renders the `mcpServers` shape shared by Cursor, Claude `.mcp.json`, and the
generic descriptor, always with `"type": "stdio"` (Cursor requires `type` for STDIO servers;
Claude Code accepts it). TOML rendering for Codex and Grok is an adapter concern in Sprint 114.2.

`Fingerprint()` is the SHA-256 of the registration's canonical JSON: it identifies the *command
Atlas registered* (name, transport, command, args), not the bytes of any client file. Ownership at
removal time is proven in two parts (review round 1, P3-3):

- `StandardServerEntry` decodes a JSON entry with its owned keys (`type`, `command`, `args`) and
  keeps every other key in `Foreign`; `Matches(reg)` is true only for a stdio entry with the exact
  command and args and **no** foreign keys, so an entry a user extended with `env`, `cwd`, or
  `headers` is not Atlas-owned and a `RemovalPlan` must set `RequiresConfirmation`.
- `IntegrationState.NativeEntryFingerprint` records the hash of the entry in the client's native
  form as Atlas wrote it (JSON, TOML, or the client CLI's listing), so drift in the file is detected
  independently of the registration identity. Canonical TOML hashing is defined by the Codex and
  Grok adapters (AT114-203, AT114-207), not by this package.

### 4.3 Deliberately absent

- No `env` in the registration. Atlas needs none, and `Command.Validate` refuses secret-looking
  environment names and credential-bearing values anyway.
- No project name, path, or raw workspace ID in the server name.
- No `delivery`/`admin` profile, no permanent approvals, no high-impact flag.

## 5. Command model (no shell interpolation)

`Command{Purpose, Executable, Args, Dir, Env, Timeout}` is the only way an adapter runs a client
binary. `Validate()` rejects:

- a relative, unclean, or empty executable, or one whose base name is a shell or script
  interpreter (`sh`, `bash`, `zsh`, `dash`, `ksh`, `fish`, `csh`, `tcsh`, `ash`, `cmd`,
  `powershell`, `pwsh`, `env`, `busybox`, `python`, `python2`, `python3`, `perl`, `ruby`, `node`,
  `nodejs`, `deno`, `bun`, with and without `.exe`);
- NUL bytes anywhere, or a `scheme://user@host` credential URL in any argument or environment
  value;
- a non-absolute `Dir`, invalid or duplicate environment names, or environment names that contain
  `TOKEN`, `SECRET`, `PASS`, `KEY`, `AUTH`, `CREDENTIAL`, `BEARER`, `COOKIE`, `SESSION`, or the
  whole word `PAT` (so `GH_PAT` is refused and `PATH` is allowed);
- a timeout of zero or above ten minutes (client CLIs that open live sessions, such as
  `openclaw mcp doctor --probe`, are documented to need well under a minute; ten minutes is the
  hard ceiling, adapters set their own shorter values).

The denylist is defence in depth, not the confinement mechanism. What actually confines execution
is the **executable tie** (review round 1, finding H): a plan's command steps and their rollbacks
must run `Detection.ExecutablePath`, detection probes must run the executable the detection
reports, and verification probes must run `Verification.ClientExecutable` (or, for `probe`, the
registered `ServerExecutable`). A standalone `Command.Validate` has no reference executable and
therefore cannot reject `/usr/bin/curl`; the tie lives at every level where one is known.

`Display()` quotes every argv element separately (never joins into a shell string).
`CommandPurpose.Mutates()` is true only for `register`, `reload`, `remove`; `Detect` and `Verify`
probes must be non-mutating and `PlanStep.Writes()` treats a read-only command step as a
non-write, which is what allows a plan to be `NoOp` while still re-inspecting the client.

## 6. Plan model

`IntegrationPlan` is deterministic (`Fingerprint()` excludes `PlanID` and `GeneratedAt`) and is the
unit AT114-002's journal applies. Validation rules that matter for review (tightened in round 1,
findings B–F; DEC-077):

- **Inputs.** `PlanInput.Home` is required; a plan whose scope is repository-carried and whose
  registration is not portable must carry `Home`, so the personal-path refusal in §4.1 is exact.
  The plan's `Scope` must be one the target documents in the matrix.
- **Containment.** Every file step path is a clean absolute path inside the workspace (never the
  root itself) or inside a `ConsentedRoots` entry (consented roots may not overlap the workspace);
  no path may contain a `.git` component anywhere, and inside the workspace the `.tracker`
  directory admits only `.tracker/integrations/**` (tracker state such as `managed-mode.json` is
  written by the service layer, never by an adapter). `record_local_state`/`remove_local_state`
  paths are inside `LocalStateRoot`, which must be absolute and outside the workspace; recorded
  state is mode `0600`.
- **Path classes.** Managed-file kinds (`write_managed_file`, `write_managed_block`,
  `remove_managed_file`, `remove_managed_block`) may touch only Atlas-owned roots for the target:
  the instruction file itself, the skill directory, `.tracker/integrations`, and the command
  directory when the client keeps one (`.claude/commands`), or a consented root; they may never
  touch a file any supported client loads as configuration. Config-entry kinds
  (`write_config_entry`, `remove_config_entry`) must carry the plan scope and may touch only the
  file the target documents for that scope with the `atlas_file_edit` write method, or a
  user-selected destination inside a consented root (the generic `user` scope of AT114-208).
- **Modes.** Writes use `0644` or `0600`; removals carry no mode.
- **Reversibility.** Every write is `reversible` with a `Rollback` or `irreversible` with an
  `IrreversibleReason`. A rollback is bound to its step: a file step is undone at its own path
  (`restore_snapshot` or `delete_created`; a removal only by `restore_snapshot`), and a command
  step is undone by `run_command` with the same executable and a `remove` or `reload` purpose.
  Read-only command steps carry no rollback.
- **Executables.** Every command step runs `Detection.ExecutablePath`, which must be set; a plan
  cannot run a binary the detection did not report.
- **Unsupported versions.** No step whose kind `TouchesClientConfig()` (`write_config_entry`,
  `remove_config_entry`, `run_client_command`) may appear.
- **Approvals.** `ApprovalStep` is reported, never executed; the plan must promise exactly the
  pending state its approval steps imply, and cannot promise a pending state without one.
- **Removal.** `Operation = remove` plans carry no registration, no approval steps, no resulting
  state, and only removal-class steps (never a `register` command); `RemovalPlan` with unverified
  ownership must set `RequiresConfirmation`.
- **Secrets.** Step descriptions, paths, and warnings may not contain credential URLs.
- **NoOp.** A `NoOp` plan has no writing steps, and a plan with no writing steps must be `NoOp`
  (except `unsupported_client_version` and `failed` results).

The validators are the fail-closed gate for everything the contract can see in a plan. Checks that
need the live filesystem (symlinks, ownership, current file identity) belong to the journal engine
of AT114-103, which records `FileIdentity{Path, Exists, Mode, Size, Owner{UID, GID}, SHA256}` for
every touched path.

### 7.1 Per-provider verified facts and consequences

**Claude Code** — source: <https://code.claude.com/docs/en/mcp>.

- Scopes `local` (default, stored per project path in `~/.claude.json`), `project` (`.mcp.json`),
  `user`; precedence local > project > user, no field merging. (V)
- Project-scoped servers show `⏸ Pending approval` until the workspace is trusted and the server is
  approved; `disabledMcpjsonServers` rejects; `claude mcp reset-project-choices` clears decisions;
  `claude -p`/SDK sessions load project servers without prompting. (V)
- `claude mcp add` with an existing name at the same scope fails ("already exists"): `Apply` must
  branch on `Detection.ExistingServers`, never retry. (V)
- `CLAUDE_PROJECT_DIR` is set in the environment of the spawned server process; the documented
  `${CLAUDE_PROJECT_DIR:-.}` example is a *shell* default that only works when the entry's command
  is itself a shell, because Claude Code does not expand variables inside a project `.mcp.json`.
  A typeless entry is stdio and `"type": "stdio"` is accepted. (V, re-read 2026-09-10 for review
  round 1)
- Reserved server names: `workspace`, `claude-in-chrome`, `computer-use`, `Claude Preview`,
  `Claude Browser`; `atlas-<hex>` cannot collide. (V)
- Consequence: preferred `project_local` needs no approval and takes an absolute path; the shared
  `.mcp.json` option is explicit, binds with `verified_cwd` (the server resolves the project
  directory it is started in and checks the expected ID), and ends in `pending_workspace_trust`
  until the human acts. Whether Claude Code starts a project-scoped stdio server with the project
  directory as its working directory is corroborated by the documentation's project-relative
  examples but is confirmed only by the AT114-204 real-client run (see §7.2).

**Codex** — sources: <https://learn.chatgpt.com/docs/extend/mcp>,
<https://learn.chatgpt.com/docs/config-file/config-reference>.

- `~/.codex/config.toml` (`$CODEX_HOME`) is the user layer; `.codex/config.toml` is a project-scoped
  override loaded only for projects marked trusted via `projects.<path>.trust_level`. (V)
- Documented `[mcp_servers.<name>]` keys: `command`, `args`, `env`, `env_vars`, `cwd`, `required`
  (default false), `enabled`, `startup_timeout_sec` (10 s), `tool_timeout_sec` (60 s),
  `enabled_tools`/`disabled_tools`, `default_tools_approval_mode` (`auto | prompt | writes |
  approve`). (V)
- `codex mcp add <name> -- <cmd...>`, `codex mcp list`, `codex mcp get`, `codex mcp remove` exist;
  the CLI writes the user-level file, so the project table is an Atlas TOML edit. (V for
  existence; write location corroborated by third-party sources only, see unverified)
- Consequence: preferred scope is the repository-carried project file with `required = false`,
  binding `verified_cwd`, resulting state `pending_workspace_trust` until the project is trusted.

**Cursor** — source: <https://cursor.com/docs/mcp> (the former `/docs/context/mcp` address
redirects here).

- `.cursor/mcp.json` (project) and `~/.cursor/mcp.json` (global); STDIO entries need `type`,
  `command`, optional `args`, `env`, `envFile`. (V)
- Variables `${env:NAME}`, `${userHome}`, `${workspaceFolder}`, `${workspaceFolderBasename}`,
  `${pathSeparator}`/`${/}` are interpolated in `command`, `args`, `env`, `url`, `headers`;
  `${workspaceFolder}` is the folder containing the `.cursor/mcp.json`. (V)
- MCP Apps are supported with fallback to normal responses; per-call tool approval; enterprise
  MCP allowlists; custom servers need a restart after updates. (V)
- Consequence: `client_variable` binding, `Restart = unverified`, `MCPApps = supported`; AT114-305
  keeps Markdown primary because project-scope widgets had a documented `resources/read` gap at
  verification time.

**OpenClaw** — source: <https://docs.openclaw.ai/cli/mcp>.

- `openclaw mcp add <name> --command <exe> --arg <a> ... --cwd <dir>`, `set`, `configure`, `unset`
  (removal, fails if absent), `list/show/status/doctor/probe --json`, `doctor --probe` and `probe`
  open a live session, `doctor` warns on literal sensitive `env`/`header` values. (V)
- `openclaw mcp reload` disposes cached runtimes for the current CLI process only; Gateway/agent
  processes need their own reload or restart. (V)
- Consequence: scope `gateway`, binding `absolute_path` via `--cwd`, cap

## 8. Deviations from the plan text

1. Two extra interface methods (`Target`, `Capabilities`) — see §2.
2. Nine states plus `ConnectionKind` instead of AT114-208's two extra state names — see §3.1
   (DEC-071).
3. `--expected-workspace-id` on every binding, not only on `verified_cwd` — see §4.1 (DEC-072).
4. `"type": "stdio"` is always rendered in JSON forms — Cursor requires it.
5. The server name is `atlas-<12 hex>` derived from the workspace UUID rather than the plan's
   illustrative `atlas-workspace_ab12cd`; the plan's requirement ("derived from workspace ID, not
   project name") is met and the name is a valid TOML bare key, JSON key, and CLI argument.
6. Claude's shared `.mcp.json` binds with `verified_cwd`, not a client variable — see §4.1
   (DEC-076). The plan's AT114-102 rule ("absolute `--workspace` where reliable, verified cwd plus
   expected ID otherwise") is applied as written; only the earlier contract draft deviated.
7. The generic target has a `user`-scope user-selected destination in the matrix so the AT114-208
   custom adapter has a documented scope; its path is chosen at setup time and must be a consented
   root (DEC-077).

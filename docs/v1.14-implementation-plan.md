# Atlas Tasker v1.14 Implementation Plan

This is the owner-approved functional plan for Atlas Tasker v1.14, the **Seamless Agent Setup +
Automatic Verified Backup** release. It is preserved here as the planning source of truth for the
release train. Progress against it is tracked ticket-by-ticket in
[docs/v1.14-acceptance.md](v1.14-acceptance.md); design decisions are recorded in
[docs/v1-decision-log.md](v1-decision-log.md) starting at DEC-070.

## Plan status and recorded owner overrides

The plan body below is reproduced as approved. Three owner directives issued after approval apply
on top of it and take precedence where they differ:

1. **Implementation ownership.** All v1.14 implementation and tests are delegated to Cursor. Codex
   is the orchestrator and independent verifier, not the implementer. The plan's closing section
   ("Master implementation instruction") was originally addressed to Codex; its naming is
   superseded by this delegation, its content is not.
2. **Release ceremony waiver.** The owner waived the procedural source/binary hashing ceremony
   (release SHA/checksum/binary attestation, "SHA-bound evidence" bookkeeping) as a completion
   gate. This waiver covers *procedural* hashing of the release artifacts only. It does **not**
   waive the integrity hashing and verification that the backup product itself requires
   (canonical tree hashes, manifest hashes, remote commit/tree/manifest verification, file-hash
   verification on restore). Functionality is proven with real tests, observed behavior, and
   complete coverage.
3. **Provider API verification.** Provider capabilities cited in the plan were re-verified against
   current official documentation during Sprint 114.0. Where the official documentation differs
   from a plan assumption, the plan text is left as approved and the verified behavior is recorded
   in [docs/v1.14-provider-adapter-contract.md](v1.14-provider-adapter-contract.md) and in the
   "Verification notes" section at the end of this document. The verified behavior governs
   implementation.

Sprint gates remain in force: no sprint begins until the prior gate has independent review with no
unresolved P0/P1.

## Release decision

Atlas Tasker v1.14 should ship as one coherent Seamless Agent Setup + Automatic Verified Backup
release.

All six existing integration targets should be included:

- Codex
- Claude Code
- Cursor
- OpenClaw
- Grok
- Generic MCP-capable agents

The public repository is currently on the v1.13.0 promotion commit,
`b95fd640c5b6bd956aadf5ac08d4b5b460e33de2`. The present integration system already detects the six
targets and installs provider-specific instructions, skills, and command templates, but it
deliberately does not register the MCP server.

Atlas also already exposes most of the necessary workflow surface through MCP, including board,
dashboard, ticket, agent, schedule, evidence, review, and handoff tools. Its existing backup system
already creates manifests and archives, verifies them, supports signatures, builds restore plans,
applies controlled restores, and runs recovery drills. That means v1.14 should extend existing
systems rather than introduce a second skill, second workflow engine, or second backup format.

## Locked product decisions

These decisions should be frozen before implementation.

### 1. Keep and expand the existing atlas-worker skill

Do not create another project-management skill.

The existing generated atlas-worker skill and provider-specific managed blocks should be updated
so that ordinary phrases activate Atlas behavior:

- "Use Atlas Tasker to manage this project."
- "What is the status?"
- "Show me the board."
- "What is blocked?"
- "Pick up the next ticket."
- "Create a ticket for this and start working."
- "Give me an update."
- "Send this for review."
- "Hand this over to Claude."
- "What changed since the last update?"

The skill must prefer MCP when connected and use the CLI only as a fallback.

### 2. Implement all six integration targets in v1.14

This is not a three-provider preview.

Each target receives:

- Detection.
- Existing skill and instruction installation.
- MCP registration where the client supports it.
- Atlas actor mapping.
- Connection verification.
- Status reporting.
- Repair.
- Safe removal.
- Upgrade reconciliation.
- Provider-specific end-to-end acceptance.

The generic target must be honest about what can be verified. Atlas can generate a portable MCP
definition and install its generic skill, but an unknown client has no universal configuration or
health-check interface. Generic status may therefore be `portable_ready` rather than falsely
reported as connected.

### 3. Default MCP permission level is workflow

The normal setup registers:

```text
tracker mcp serve
  --workspace <verified workspace>
  --tool-profile workflow
  --max-items 30
  --max-result-bytes 65536
```

The exact arguments should be represented structurally, not assembled through a shell string.

The workflow profile is appropriate because it exposes ordinary local project-management actions
while leaving sync push/pull, merge, import application, archive restoration, gate waivers, and
other high-impact operations outside ordinary onboarding.

Setup must not enable:

- `delivery`
- `admin`
- `--dangerously-allow-high-impact-tools`
- permanent high-impact approvals

Those remain separate, explicit power-user operations.

### 4. Project-specific integration is the default

No agent should accidentally receive access to every Atlas workspace on the computer.

The registration must bind:

- Atlas workspace ID.
- Canonical workspace path or verified project context.
- Absolute trusted tracker executable.
- Tool profile.
- Integration ID.
- Provider.
- Default Atlas actor hint.
- Result-size limits.

Codex supports project-scoped `.codex/config.toml`; Claude supports local and project scopes;
Cursor supports `.cursor/mcp.json`; OpenClaw has CLI registration and a live probe; and Grok Build
supports project-scoped MCP registration and a doctor command. (Verified against official
documentation; see the capability matrix.)

### 5. Do not bypass provider security approval

Some clients may still require:

- Workspace trust.
- Project MCP approval.
- A restart.
- Tool-use confirmation.
- An administrator policy exception.

Atlas should automate everything the provider safely exposes, then report one of these exact
states:

```text
connected
connected_restart_required
pending_workspace_trust
pending_mcp_approval
configured_unverified
portable_ready
unsupported_client_version
repair_required
failed
```

Atlas must never click through, suppress, or rewrite a provider security approval to make setup
appear more seamless.

### 6. Agent integration and off-device backup require separate consent

One setup flow can offer both, but they are separate transaction groups.

Agent integration changes local instructions and client configuration.

Off-device backup transmits Atlas-owned data — tickets, events, comments, evidence, governance
state, and other records — to another Git repository. Backup must therefore receive separate
approval and a clear data-boundary confirmation.

Failure to configure backup must not undo successful agent integrations.

### 7. Automatic backup is not normal-branch auto-commit

Do not run:

```bash
git add -A
git commit
git push
```

Do not alter:

- The user's current branch.
- The user's index.
- Staged source changes.
- Unstaged source changes.
- Untracked files.
- Merge/rebase/cherry-pick state.
- Existing origin.

Automatic backups use an Atlas-owned isolated Git repository and history.

### 8. Back up Atlas state, not source code

The v1.14 Git checkpoint contains the same Atlas-owned canonical state selected by the existing
verified backup collector, plus a checkpoint manifest.

It does not include the project's application source merely because source files happen to share
the repository.

### 9. Automatic backups are asynchronous to ticket mutations

Moving or closing a ticket must not fail because GitHub, DNS, SSH, or the network is unavailable.

The mutation commits locally first. Atlas then records a durable pending-backup watermark. A
background worker creates and pushes the checkpoint later.

### 10. Restore is always explicit and preview-first

Automatic backup does not imply automatic pull or restore.

A remote checkpoint must be:

1. Fetched into temporary storage.
2. Verified.
3. Converted into the existing Atlas restore-plan model.
4. Previewed.
5. Explicitly approved.
6. Applied under the normal write lock.
7. Reindexed and checked with doctor.

## Target architecture

### Seamless setup path

```text
tracker setup
    │
    ├── inspect workspace and current Atlas state
    ├── detect six supported integration targets
    ├── inspect provider versions and existing MCP configuration
    ├── inspect existing agents, team policy, and completion policy
    ├── create deterministic setup plan
    ├── collect agent-integration consent
    ├── collect separate backup consent
    ├── apply each provider transaction independently
    ├── verify each skill and MCP connection
    ├── configure managed project mode
    ├── configure automatic backup when selected
    ├── run first checkpoint and remote verification
    └── persist local setup/ownership manifest
```

### Agent-managed work path

```text
User asks agent to perform material project work
    │
    ├── existing atlas-worker skill activates
    ├── agent calls atlas.context
    ├── agent searches for an existing ticket
    ├── agent creates one only when policy allows and none exists
    ├── agent claims and starts work
    ├── agent records milestone progress and evidence
    ├── agent follows review/completion policy
    └── agent reconciles Atlas state before reporting completion
```

### Status path

```text
User: "What's the status of APP?"
    │
    ├── skill requires fresh Atlas read
    ├── atlas.status resolves project APP
    ├── queries board, blockers, reviews, agents, recent changes
    ├── returns structured content
    ├── returns deterministic Markdown fallback
    └── optionally returns a read-only MCP App board
```

### Automatic backup path

```text
Successful Atlas mutation
    │
    ├── append canonical event and state
    ├── update durable pending watermark
    └── return success to caller

Backup worker
    │
    ├── observes quiet-period or maximum-delay trigger
    ├── captures consistent Atlas-only snapshot
    ├── computes canonical tree and manifest
    ├── creates commit in isolated backup repository
    ├── pushes fast-forward to replica-specific remote ref
    ├── fetches/verifies exact remote commit
    └── records verified recovery point
```

## Storage and state model

### Shared, repository-carried state

These may be committed to the project repository:

- Existing Atlas Markdown and event records.
- Existing generated provider instructions.
- Existing provider skill files.
- Managed project-mode policy.
- Optional portable MCP configuration intended to travel with the repository.

No machine-specific absolute paths. No credentials.

### Local machine-only integration state

Store under an operating-system-appropriate private data directory, for example:

```text
macOS:
~/Library/Application Support/Atlas Tasker/

Linux:
$XDG_STATE_HOME/atlas-tasker/
$XDG_CONFIG_HOME/atlas-tasker/
```

This state contains:

- Workspace registry.
- Canonical workspace path.
- Workspace ID.
- Local replica ID.
- Installed tracker executable identity.
- Provider versions.
- Provider configuration locations.
- Atlas-owned configuration entry fingerprints.
- Before/after configuration hashes.
- Verification state.
- Repair state.
- Backup target definitions.
- Backup worker state.

Permissions:

```text
directory: 0700
files:     0600
```

It must be excluded from normal Atlas exports, sync bundles, backups, and diagnostics.

### Setup manifest

Use a versioned model similar to:

```json
{
  "format": "atlas_setup_v1",
  "workspace_id": "workspace_...",
  "workspace_path": "/canonical/local/path",
  "tracker_binary": {
    "path": "/usr/local/bin/tracker",
    "sha256": "...",
    "version": "1.14.0"
  },
  "managed_mode": {
    "enabled": true,
    "capture_policy": "material_work",
    "status_source": "atlas_required"
  },
  "integrations": {
    "codex": {
      "state": "connected",
      "server_name": "atlas-workspace_ab12cd",
      "actor": "agent:builder-1",
      "adapter_version": 1
    }
  },
  "backup": {
    "enabled": true,
    "target_id": "backup_target_...",
    "replica_id": "replica_..."
  },
  "schema_version": 1
}
```

Do not put credentials, terminal output, ticket text, or provider authentication tokens in this
manifest.

### Automatic-backup manifest

```json
{
  "format": "atlas_git_checkpoint_v1",
  "checkpoint_id": "checkpoint_...",
  "workspace_id": "workspace_...",
  "replica_id": "replica_...",
  "atlas_version": "1.14.0",
  "created_at": "RFC3339 timestamp",
  "canonical_tree_sha256": "...",
  "manifest_sha256": "...",
  "previous_checkpoint_commit": "...",
  "event_watermarks": {
    "workspace": "...",

  },
```

Do not assume Atlas has one globally sequential event ID. Inspect the existing event model and

**Acceptance**

- Exact base SHA and tree recorded.
- Tracked and untracked state clean before implementation.
- First implementation commit has the approved baseline as direct parent.
- No merge of unrelated work during the release train.
- Baseline test suite passes.

**Verification**

- `git rev-parse HEAD`
- `git rev-parse HEAD^{tree}`
- `git status --short --untracked-files=all`
- Existing release rehearsal.
- Existing MCP workflow verification.
- Existing installer tests.
- Existing backup and sync tests.

### AT114-002 — Unified setup ADR and transaction model

**Implementation**

Document:

- `tracker init` remains low-level workspace initialization.
- `tracker setup` is the high-level orchestrator.
- Every setup run begins with a read-only plan.
- Provider integrations are separate atomic transactions.
- Backup is a separate transaction group.
- Partial success is represented honestly.
- Setup is idempotent.
- Repair and removal use the same adapter contracts.
- No global provider state is modified without explicit consent.
- No agent software is installed by Atlas.
- Provider trust dialogs are never bypassed.

Define operation states:

```text
planned
applying
applied
verifying
connected
pending_approval
failed
rolling_back
rolled_back
repair_required
```

**Acceptance**

- No setup operation can write before a complete plan exists.
- Every write has a corresponding rollback or explicit irreversible classification.
- Config snapshots do not contain credentials.
- Interrupted setup can resume or roll back safely.

### AT114-003 — Provider adapter contract and capability matrix

**Implementation**

Create a common interface:

```go
type AgentIntegrationAdapter interface {
    Detect(ctx context.Context, input DetectInput) Detection
    Plan(ctx context.Context, input PlanInput) (IntegrationPlan, error)
    Apply(ctx context.Context, plan IntegrationPlan) (ApplyResult, error)
    Verify(ctx context.Context, state IntegrationState) (Verification, error)
    Repair(ctx context.Context, state IntegrationState) (RepairPlan, error)
    Remove(ctx context.Context, state IntegrationState) (RemovalPlan, error)
}
```

Each provider adapter must report:

- Client installed.
- Client version.
- Skill support.
- MCP support.
- Supported scope.
- Configuration path.
- Verification method.
- Approval requirement.
- Restart requirement.
- Whether config is local or repository-carried.
- Whether removal is safely supported.

**Acceptance**

- All six targets implement the same interface.
- Unknown versions fail to `unsupported_client_version`; Atlas does not heuristically modify
  unknown config.
- Generic is represented as portable, not falsely verified.
- No adapter uses shell interpolation.

### AT114-004 — Managed project-mode contract

**Implementation**

Add a versioned policy:

```json
{
  "format": "atlas_managed_mode_v1",
  "mode": "managed",
  "capture_policy": "material_work",
  "progress_policy": "milestones",
  "status_policy": "query_atlas",
  "completion_policy": "follow_workspace",
  "mcp_preferred": true
}
```

Modes:

- `guidance`: skills only.
- `managed`: skills, MCP, status, ordinary workflow.
- `delivery`: separately enabled advanced operations.
- `disabled`.

Define material work as work expected to modify the repository, create an implementation artifact,
run a substantive review, or produce a durable project deliverable.

Do not create tickets for:

- Casual discussion.
- Read-only explanation.
- A status query.
- A simple question with no project change.
- A user instruction explicitly excluding tracking.

**Acceptance**

- Existing completion and review policies remain authoritative.
- Managed mode cannot waive dependencies, governance, review, or approval.
- Agent identity is always explicit in writes.
- No agent silently self-approves where policy forbids it.

### AT114-005 — Automatic-backup ADR and threat model

**Implementation**

Freeze:

- Backup is not sync.
- Backup never pulls automatically.
- Backup never merges automatically.
- Backup never force-pushes.
- Existing origin is never selected automatically.
- Remote target is explicitly configured.
- Private Git target is the v1.14 provider.
- Backup repository is isolated from the user's working repository.
- Checkpoints contain Atlas-owned canonical data only.
- Remote backup is plaintext within the Git repository.
- Encrypted archive/object-store providers are deferred.
- Normal mutations remain successful during remote failure.
- Restore remains explicit.

Threat model must include:

- Source-code capture.
- Secret capture.
- Credential-bearing remote URLs.
- Public repository selection.
- Git index contamination.
- Git lock interference.
- Symlink escapes.
- Path traversal.
- Backup recursion.
- Remote divergence.
- Multiple replicas.
- Interrupted push.
- Malicious checkpoint.
- Restore into conflicting state.
- Ransomware or local workspace deletion.

## Sprint 114.1 — unified setup engine

### AT114-101 — Deterministic setup planner

**Implementation**

Add:

```text
tracker setup --plan
tracker setup --plan --json
tracker setup --agents all --plan
tracker setup --backup --plan
```

The planner inspects:

- Workspace initialization.
- Workspace identity.
- Existing projects and agents.
- Existing team/completion policies.
- All six client detections.
- Existing managed instruction blocks.
- Existing provider MCP registrations.
- Existing setup manifest.
- Existing backup state.
- Existing backup target.
- Scheduler state.

The plan contains exact:

- Files to create or update.
- Provider commands to execute.
- Configuration stanzas to add.
- Entries to remove.
- Permissions.
- External side effects.
- Approval/trust steps.
- Rollback steps.

**Acceptance**

- Planning performs no writes.
- Planning performs no remote calls except optional read-only provider detection explicitly shown
  in the plan.
- Two identical inputs generate semantically identical plans.
- Secret values are never rendered.

### AT114-102 — Secure workspace registry and portable workspace resolution

**Implementation**

Add a local machine registry keyed by workspace ID.

Introduce a secure project resolution mode for project-scoped MCP clients:

```text
tracker mcp serve
  --workspace-from-cwd
  --expected-workspace-id <ID>
```

Security requirements:

- No initialization.
- Canonicalize the current directory.
- Walk only to the nearest valid Atlas root.
- Refuse nested workspace ambiguity.
- Verify the expected workspace ID.
- Reject symlink substitutions.
- Reject a replaced workspace.
- Never fall back to another known workspace.
- Never use an unverified registry path.

Use absolute `--workspace` where the provider supports a reliable local-project registration. Use
the verified current-project mode only where a provider's project config cannot safely carry an
absolute machine path.

**Acceptance**

- Wrong cwd fails.
- Wrong workspace ID fails.
- Nested workspace fails.
- Moved workspace reports repair required.
- A copied workspace with the same stale local registration fails until reconciled.
- No client can select a different workspace through MCP arguments.

### AT114-103 — Setup journal and rollback engine

**Implementation**

Before any provider or local config change:

1. Acquire a setup lock.
2. Validate every target path.
3. Record existing file identity, mode, ownership, and SHA-256.
4. Create private rollback material.
5. Apply one provider transaction.
6. Verify.
7. Commit local integration state.
8. Delete or rotate rollback material according to policy.

The journal must survive process interruption.

Provider failure must roll back only that provider's incomplete transaction. Successful unrelated
providers remain connected.

**Acceptance**

Crash-injection points:

- Before first write.
- After config snapshot.
- After instruction update.
- After MCP config update.
- After provider CLI exits.
- After verification but before manifest commit.
- During rollback.

Every point must resume or return to the prior verified state.

### AT114-104 — `tracker setup` interactive and noninteractive execution

**Implementation**

Add:

```text
tracker setup
tracker setup --yes
tracker setup --agents codex,claude,cursor,openclaw,grok,generic
tracker setup --mode managed
tracker setup --team pair
tracker setup --backup-target <ID>
tracker setup --json
```

Interactive mode:

- Preselects detected named agents.
- Leaves generic as an explicit selection unless a portable client is detected.
- Detects existing team policy before suggesting changes.
- Does not overwrite existing agent roles silently.
- Obtains distinct backup consent.

Noninteractive mode requires all external-impact decisions as flags. Missing decisions fail before
writing.

**Acceptance**

- Re-running setup is a no-op when current.
- `--json` writes only JSON to stdout.
- Interactive cancellation writes nothing.
- EOF is not treated as consent.
- Backup failure returns partial success without corrupting connected agents.

### AT114-105 — Setup state, status, repair, and removal

**Implementation**

Add:

```text
tracker setup status
tracker setup status --json
tracker setup repair
tracker integrations status
tracker integrations repair <target>
tracker integrations disconnect <target>
```

Status includes:

- Skill version.
- Managed-block version.
- MCP registration.
- MCP profile.
- Provider version.
- Workspace binding.
- Actor mapping.
- Approval/restart state.
- Backup worker state.
- Last verified checkpoint.
- Repair reason.

Removal deletes only Atlas-owned entries whose fingerprint still matches. If the user changed an
Atlas-managed entry, produce a removal plan and require confirmation.

**Acceptance**

- Unrelated provider settings remain byte-for-byte unchanged.
- Removal does not delete custom instructions outside managed markers.
- Repair handles binary relocation, workspace relocation, stale skill files, and changed config
  formats.
- Ambiguous ownership fails closed.

### AT114-106 — Installer handoff

**Implementation**

The shell installer remains responsible for:

- Download.
- Checksum verification.
- Attestation verification.
- Binary installation.

After an explicit interactive choice, it invokes:

```text
tracker setup
```

It no longer owns a second integration workflow based on `tracker init --integrations`.

Noninteractive install never initializes the current directory.

**Acceptance**

- Existing installer security remains unchanged.
- Older pinned versions fall back safely.
- Setup failure does not remove a correctly installed binary.
- Installer tests cover yes, no, EOF, non-TTY, custom `BIN_DIR`, and old-version behavior.

## Verification notes (Sprint 114.0)

Provider claims in the plan were checked against official documentation on 2026-09-10. The
following verified facts refine plan assumptions and govern the adapters in Sprint 114.2. The full
per-provider matrix, with the source of each fact, is in
[docs/v1.14-provider-adapter-contract.md](v1.14-provider-adapter-contract.md).

- **Codex.** Project-scoped `.codex/config.toml` is loaded only for projects the user has marked
  trusted (`projects.<path>.trust_level`), which maps to `pending_workspace_trust`. The
  `codex mcp add/list/get/remove` CLI operates on the user-level `~/.codex/config.toml`
  (`$CODEX_HOME`); the project-scoped table must be written by Atlas as a TOML edit and can be
  inspected with `codex mcp list`/`codex mcp get` from a trusted project directory.
  `mcp_servers.<name>.required` (default false), `enabled`, `cwd`, `startup_timeout_sec`
  (default 10s), `tool_timeout_sec` (default 60s), `enabled_tools`/`disabled_tools`, and
  `default_tools_approval_mode` (`auto | prompt | writes | approve`) are documented keys. The
  official reference describes project files as "project-scoped overrides" of the user layer.
- **Claude Code.** Scopes are `local` (default; `~/.claude.json` keyed by project path),
  `project` (`.mcp.json`), and `user`. Precedence is local > project > user, with no field merging
  across scopes. Project-scoped servers show `⏸ Pending approval` until the workspace is trusted
  and the server approved interactively; `disabledMcpjsonServers` rejects a server everywhere;
  `claude mcp reset-project-choices` clears decisions. Re-adding an existing name at the same
  scope fails ("already exists"), so apply must detect existing entries rather than retry. Server
  names `workspace`, `claude-in-chrome`, `computer-use`, `Claude Preview`, and `Claude Browser`
  are reserved.
- **Cursor.** `.cursor/mcp.json` (project) and `~/.cursor/mcp.json` (global) are merged with the
  project entry winning on a name collision. Cursor resolves `${workspaceFolder}`,
  `${workspaceFolderBasename}`, `${userHome}`, `${env:NAME}`, and `${pathSeparator}` in
  `command`, `args`, `env`, `url`, and `headers`. MCP Apps are supported with automatic fallback to
  normal responses; at the time of verification, widgets from project-scoped servers had a known
  issue where `resources/read` is not issued and the result falls back to text. AT114-305 must
  treat Markdown as the primary presentation for Cursor project-scoped registrations.
- **OpenClaw.** Registration is `openclaw mcp add <name> --command ... --arg ... --cwd ...`;
  removal is `openclaw mcp unset <name>` (fails if absent). `doctor` is static, `doctor --probe`
  and `probe` open a live session; `--json` is available on `list`, `show`, `status`, `doctor`,
  and `probe`. `openclaw mcp reload` disposes cached runtimes for the current CLI process only;
  Gateway or agent processes need their own reload or restart, which maps to
  `connected_restart_required`. `doctor` warns on literal sensitive `env`/`header` values.
- **Grok Build.** `grok mcp add --scope project` writes `.grok/config.toml` in the current
  directory; Grok walks from cwd to the git root reading each `.grok/config.toml`, and a project
  server with the same name replaces a user server entirely. `grok mcp list --json`,
  `grok mcp doctor [name] --json`, and `grok mcp remove <name>` exist; `grok inspect` shows every
  loaded server and its origin. Grok also imports MCP definitions from `~/.claude.json`,
  `.cursor/mcp.json`, and project `.mcp.json` below `config.toml` in priority unless
  `[compat.claude] mcps = false` / `[compat.cursor] mcps = false`, which is the duplicate-catalog
  risk AT114-207 must handle. Project `.grok/config.toml` contributes only `[mcp_servers]`,
  `[plugins]`, and `[permission]`.
- **Result-bounding flags.** `tracker mcp serve` in v1.13.0 already accepts `--max-items`
  (default 50), `--max-result-bytes` (default 131072), and `--max-text-tokens-estimate`
  (default 4000) in `internal/cli/mcp.go`. The canonical registration's `30` and `65536` are
  deliberate tightenings of those defaults, not new flags.

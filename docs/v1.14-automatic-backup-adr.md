# ADR: Automatic Verified Backup and Threat Model (AT114-005)

Status: Sprint 114.0 architecture decision, revised after independent review round 1 (findings
B-A..B-H and G-A; dispositions in [release/v1.14-s0-review-round1.md](release/v1.14-s0-review-round1.md)).
Recorded as DEC-074 (with its round-1 revisit note) in [v1-decision-log.md](v1-decision-log.md).
Implemented by Sprints 114.4 (local checkpoints, AT114-401..407) and 114.5 (off-device Git backup
and restore, AT114-501..507).

## 1. Frozen rules

1. Backup is not sync. It never changes the workspace; the existing `sync` subsystem is untouched.
2. Backup never pulls, never merges, never force-pushes, never rebases.
3. The existing `origin` (or any remote of the user's repository) is never selected automatically;
   a backup target is configured explicitly and stored in machine-local state.
4. The v1.14 provider is a private Git repository reachable over SSH or HTTPS with the user's
   existing SSH agent or credential helper. Encrypted archive and object-store providers are
   deferred.
5. The backup repository is an Atlas-owned bare repository outside the workspace. Atlas never
   runs Git with the user's repository as `GIT_DIR` or work tree.
6. Checkpoints contain Atlas-owned canonical data only: exactly the file set the existing verified
   backup collector selects, plus one checkpoint manifest.
7. Remote content is plaintext inside the Git repository; the confidentiality boundary is the
   repository's own access control, which is why rule 3 and the private-target attestation exist.
8. Ordinary Atlas mutations succeed whether or not the remote is reachable; backup is asynchronous
   and its failures are reported as degraded backup health, never as mutation errors.
9. Restore is explicit, preview-first, and reuses the existing restore-plan/apply boundary.
10. Backup activity never appends to the canonical event log (see §4.4), so a checkpoint cannot
    trigger the next checkpoint.

## 2. What is backed up

The checkpoint tree is `backupRestoreSafeFiles(collectExportFiles(root))` from
`internal/service/import_export.go` and `internal/service/backup_goal_actions.go`, the same
selection `tracker backup create` uses today, extracted by AT114-401 into one shared snapshot
builder with the two corrections of §2.1:

- `collectExportFiles` walks a fixed candidate list (`projects`, `.tracker/config.toml`,
  `.tracker/events`, agents, automations, views, subscriptions, runbooks, runs, gates, handoffs,
  evidence, changes, checks, permission-profiles, imports, retention, security public keys /
  revocations / signatures, governance, classification, redaction rules, audit reports/packets),
  rejects symlinks (`export_symlink_rejected`), and skips runtime, archives, exports, mutations,
  `.log`, and the SQLite index.
- `backupRestoreSafeFiles` keeps only paths that `contracts.RestorePlanItem.Validate()` accepts,
  i.e. the `isCanonicalRestorePlanPath` allowlist: Markdown under `projects/` and the `.tracker`
  record directories, TOML policy files, JSON signatures/audit files, and `.tracker/events/*.jsonl`.

Never included: application source, `.git`, the SQLite index, `.tracker/mutations`,
`.tracker/runtime`, exports payloads, `.tracker/backups/*` (existing backup manifests and snapshot
archives), `.tracker/security/keys/private`, local machine state, and anything outside the
workspace.

### 2.1 Allowlist and candidate-list parity (review finding B-A, resolved)

The two selection layers disagree in both directions today, and `tracker backup create` inherits
both gaps:

1. **Exported but not restore-safe.** `collectExportFiles` exports `.tracker/config.toml`,
   `.tracker/agents`, `.tracker/views`, `.tracker/automations`, `.tracker/subscriptions`,
   `.tracker/runbooks`, and `.tracker/imports`, but `isCanonicalRestorePlanPath` does not accept
   them, so `backupRestoreSafeFiles` drops them from every restore-safe backup. **Decision:** the
   v1.14 checkpoint inherits this unchanged in Sprint 114.4; the recovery drill (AT114-507) must
   show which of these `tracker init`/`tracker setup` re-create and which are lost, and AT114-401
   extends the allowlist for exactly the record kinds the drill proves necessary (a `[SHARED]`
   change to `internal/contracts/backup.go` with restore-plan tests). `.tracker/managed-mode.json`
   (AT114-004) is a new record that takes the same route (AT114-301).
2. **Restore-safe but never collected.** `isCanonicalRestorePlanPath` accepts
   `.tracker/collaborators/*.md`, `.tracker/memberships/*.md`, `.tracker/mentions/*.md`, and
   `.tracker/archives/**/*.md`, but `collectExportFiles` never walks those directories (it skips any
   `/archives` path outright). Collaborator and membership records are the identity inputs to
   permission evaluation, so a disaster-recovery restore today reproduces governance *policies*
   without the identities they refer to. **Decision:** AT114-401's shared snapshot builder adds
   `collaborators`, `memberships`, and `mentions` to the candidate list (already restore-safe, so no
   allowlist change), and adds archive records (`.tracker/archives/<id>.md`) together with their
   Markdown payloads (`.tracker/archives/<id>/**/*.md`): archives are canonical data the retention
   subsystem moved out of the live directories, and a restore that brought back records without
   payloads would leave `archive restore` unable to complete. The existing size limits apply to the
   whole tree. Non-Markdown payload files are not produced today and stay excluded by the
   allowlist.
3. **Parity test.** AT114-401 adds a test that every prefix `isCanonicalRestorePlanPath` accepts is
   either a collector candidate or in a named "intentionally excluded" list, and that every
   collector candidate is either restore-safe or in a named "exported only" list, so neither gap
   can reopen silently.

### 2.2 Governance on restore (review finding G-A, resolved)

`backup_restore` is a defined `ProtectedAction`, but `ApplyRestorePlan`
(`internal/service/backup_goal_actions.go`) never evaluates it: it checks `--yes`, actor validity,
reason, integrity, and blocked items, then writes inside `commitMutation`. Archive restore, import
apply, and export create all call `requireGovernance`. Restore is the one mutation that can rewrite
identity records, governance policies, and permission profiles in a single write, so a policy
authored for `backup_restore` today is accepted and silently never enforced.

**Decision:** AT114-506 adds `requireGovernance{Action: backup_restore, Target: workspace}` to
`ApplyRestorePlan` after plan construction and before `commitMutation`, following the
`ArchiveRestore` pattern. A denying policy yields `permission_denied` (exit 5) with zero files
written; an allowing or absent policy leaves behavior unchanged. `--yes` remains the interactive
guard, never the authorization. v1.14 remote restore (§5 step 5) inherits the check through the
boundary. This is a `[SHARED]` change to `internal/service` with both tests. `CreateBackup` has no
protected action defined and none is added: creating a checkpoint reads canonical data and writes
outside the workspace. `ApplyRestorePlan` also does not rebuild the projection or run doctor; the
remote restore command adds both steps explicitly around the existing boundary.

## 3. Architecture

```text
mutation (commitMutation)                       backup worker (tick / watch / scheduler)
  canonical write ─ event append ─ projection      trigger: 30 s quiet, 5 min max delay, 100 pending
  journal.Complete                                 read outbox + watermarks
  post-commit hooks: Notifier, wakeups,            snapshot: shared canonical builder (§2) copies the
    Automation, + v1.14 backup outbox mark            tree under the exclusive workspace write lock
    (machine-local, never an event)                   into a private temp dir, then releases it
                                                   canonical tree hash + manifest (§4.2), outside the lock
                                                   commit in the isolated bare repo (plumbing only)
                                                   push fast-forward to the replica ref
                                                   fetch/verify exact remote commit, tree, manifest
                                                   record verified recovery point (local ledger)
```

**Locking** (review finding B-B). Atlas has one workspace lock, the exclusive
`flock(LOCK_EX|LOCK_NB)` in `internal/service/lock.go` with a bounded wait and exit 6 (`busy`);
there is no shared or read lock. The checkpoint therefore copies the candidate files under the
exclusive write lock, holds it only for the copy (bounded by the same wait the CLI uses, and by a
per-checkpoint copy budget AT114-401 fixes and tests), and hashes, commits, pushes, and verifies
outside it. When a checkpoint and a writer collide, the checkpoint yields: it treats `busy` as a
retry with backoff, never as a failure, and the writer is never delayed by more than one copy.

### 3.1 Outbox and watermarks

- The outbox is a machine-local, durable, reconstructable file in the private state directory: it
  records "pending since" and the per-stream watermarks at the last verified checkpoint. Losing it
  costs nothing but an extra checkpoint: the worker can always compare the current canonical tree
  hash with the last verified checkpoint's `canonical_tree_sha256`.
- Atlas has no global sequential event ID. `contracts.Event.EventID` is monotonic per project
  stream (`.tracker/events/` records carry `project_key`, `event_id`, `origin_workspace_id`,
  `logical_clock`), and workspace-scoped records (agents, backups) use the `_workspace` pseudo
  project (`workspaceProjectKey` in `internal/service/agent_store.go`). Watermarks are therefore a
  map `stream -> max event_id` with `workspace` for the `_workspace` stream and one entry per
  project key, exactly as the plan's manifest sketch shows. The canonical tree hash, not the
  watermarks, is the authoritative "has anything changed" test; watermarks are diagnostics and
  trigger counters.
- The outbox mark is written by a new post-commit hook in `commitMutation` after
  `journal.Complete`, next to `emitAgentWakeups` and `Automation.Run`, and is skipped during
  historical replay like those hooks. A failure to write the mark is logged and never fails the
  mutation (rule 8); the tree-hash comparison recovers the missed trigger.

### 3.2 Isolated Git repository

- Location: private state directory, `backups/<workspace-id>/repo.git`, bare, created by Atlas with
  `core.hooksPath` pointing at an empty Atlas-owned directory and no remotes configured except the
  explicit backup target.
- Every Git invocation sets `GIT_DIR` to that repository, unsets `GIT_WORK_TREE`,
  `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`,
  and `GIT_CONFIG_PARAMETERS`/`GIT_CONFIG_COUNT`, sets `GIT_TERMINAL_PROMPT=0`, and runs with the
  temp snapshot directory as cwd, never the user's checkout. The user's global and system Git
  configuration is **not** masked (review finding B-E): credential helpers, `url.<base>.insteadOf`,
  `core.sshCommand`, and `http.*` proxy settings live there and are exactly what rule 4 relies on.
  Only what must be pinned is pinned, per invocation with `-c`: `commit.gpgsign=false`,
  `tag.gpgsign=false`, `core.hooksPath=<empty Atlas-owned dir>`, `protocol.allow=never` with
  `protocol.ssh.allow=always` and `protocol.https.allow=always`, and `credential.interactive=never`.
- Commits are built with plumbing (`hash-object -w`, `update-index` on a private temp index,
  `write-tree`, `commit-tree`, `update-ref`), so no hook, no porcelain staging, and no interaction
  with the user's `HEAD`, branch, index, staged/unstaged/untracked files, or in-progress
  merge/rebase/cherry-pick state. Tree entries are regular blobs (mode `100644`) only.
- The remote ref is `refs/atlas/backups/<workspace-id>/<replica-id>`; never `refs/heads/*`, so a
  backup target that is also somebody's working repository gets no branch, tag, or default-branch
  change. The local repository mirrors that single ref.

### 3.3 Publication and verification

- Push is `git push <target> <commit>:refs/atlas/backups/<ws>/<replica>` without `--force` and
  with the expected remote tip checked first (`ls-remote`); a mismatch is `diverged`, never a
  force. Authentication is whatever the user's SSH agent or credential helper provides
  (`BatchMode=yes`, no prompts); an auth failure is a degraded state.
- The `ls-remote` check and the push are two round trips, not a compare-and-swap (review finding
  B-E). `--force-with-lease=<ref>:<expected-oid>` would close that window, but locked decision 6
  and rule 2 say backup never force-pushes, and a lease is still a force under the wire protocol
  and in every server-side audit log, so it is not used. The residual race is benign by
  construction: the ref is per replica (§3.4) and only this machine's worker, serialised by the
  local ledger lock, pushes to it, so the only writer that can advance the ref between the two
  round trips is a misconfigured second machine reusing this replica ID. In that case the
  server's own fast-forward check rejects the push, the worker reports `diverged`, and `backup
  reconcile` assigns a fresh replica ID; nothing is overwritten in either ordering.
- After the push, the worker `ls-remote`s the ref, fetches the exact commit into the local
  repository, and verifies commit ID, tree ID, and the manifest blob hash against what it pushed.
  Only then is the checkpoint recorded as verified in the local ledger.
- Target configuration compares the backup URL with every remote of the workspace's own Git
  repository (`git -C <root> remote -v`, read-only) and warns when they match (review finding
  B-F): a hidden `refs/atlas/*` namespace on the project's `origin` is deleted by any
  `git push --mirror` or ref prune from another clone and may surprise repository administrators.
  The warning is repeated in `backup status`; the user may proceed after acknowledging it.

### 3.4 Replicas

Each machine holding the workspace gets a `replica_id` in local state; refs are per replica, so two
machines never contend for one ref, and a restore lists checkpoints from every replica ref under
the workspace prefix. A copied workspace (same workspace ID, no local state) is treated as a new
replica after explicit `backup reconcile`, never as the original.

### 3.5 Trigger policy

Quiet period 30 s after the last mutation; maximum unbacked delay 5 min; immediate checkpoint at
100 pending events; explicit `tracker backup tick` (one pass) and `tracker backup watch`
(foreground loop); consented user-level launchd/systemd scheduling (AT114-505). No root, no hidden
service from `tracker init`. Pre-destructive checkpoints (before restore apply, import apply,
archive restore) are explicit calls into the same builder (AT114-406).

## 4. Data model

### 4.1 Checkpoint manifest `atlas_git_checkpoint_v1`

Fields as in the plan: `format`, `checkpoint_id`, `workspace_id`, `replica_id`, `atlas_version`,
`created_at`, `canonical_tree_sha256`, `manifest_sha256`, `previous_checkpoint_commit`,
`event_watermarks` (`workspace` + project keys), `file_count`, `schema_version`, plus a per-file
list `{path, sha256, size}` sorted by path, which is what restore verifies file by file. The
manifest is committed as `.atlas-checkpoint.json` at the tree root; the canonical tree hash is the
SHA-256 over the sorted `path\0sha256\0size\n` lines excluding the manifest itself, so it is
independent of Git's object format and reproducible without Git.

`manifest_sha256` is defined, not self-referential (review finding B-D): it is the SHA-256 of the
canonical encoding of the manifest (keys sorted, no insignificant whitespace, UTF-8, trailing
newline) with the `manifest_sha256` field set to the empty string. The committed manifest carries
the computed value; a verifier re-encodes the parsed document with the field blanked, hashes it,
and compares. AT114-401 pins the encoding with a golden-file test and AT114-402 pins the round trip
(encode → hash → parse → verify), so a manifest edited after the fact is detected before any tree
entry is trusted. This is product integrity hashing, which the owner's waiver of release SHA
ceremonies does not touch.

### 4.2 Local ledger

Machine-local, private: last verified checkpoint (commit, tree hash, manifest hash, time), pending
watermarks, degraded-state reason, retry schedule, target ID, replica ID. Excluded from exports,
sync bundles, backups, and diagnostics like all local state.

### 4.3 Backup target `atlas_backup_target_v1`

Machine-local: `target_id`, `url` (validated: no userinfo, scheme `ssh`/`https`/scp-like SSH
syntax only), `visibility_attestation: private` typed by the user, `created_at`, `last_verified`.
The URL is validated with the same credential-URL rejection the adapter `Command` model uses.

### 4.4 No canonical backup events

The existing `tracker backup create` appends a `backup.created` event and `ApplyRestorePlan` a
`backup.restored` event to the canonical log (`backup.verified` and `backup.restore_planned` are
defined in `contracts/events.go` but emitted by nothing). v1.14 automatic checkpoints do **not**
append any event: an appended event would change the checkpoint tree and produce an endless chain
of one-event checkpoints. Checkpoint history lives in the local ledger and in the backup repository
itself; `atlas.status` and `tracker backup status` read it from there. Explicit `tracker backup
create` keeps its current behavior; a remote restore keeps `backup.restored`, which is correct
because a restore is a workspace mutation.

## 5. Restore

`tracker backup restore --from <target> [--replica <id>] [--checkpoint <id>]`:

1. Fetch the selected ref into a temporary bare repository (never the workspace, never the user's
   `.git`).
2. Verify: commit reachable from the ref, manifest parses as `atlas_git_checkpoint_v1`,
   `workspace_id` matches the current workspace (or `--allow-workspace-mismatch` with a printed
   warning for disaster recovery into a fresh workspace), `manifest_sha256` matches, every tree entry
   is a `100644` blob whose path passes `isSafeRestorePlanPath` and whose SHA-256 matches the
   manifest, `file_count` matches, no extra entries, total size within limit.
3. Materialize only those paths into a temp directory and build a `contracts.RestorePlan` through
   the existing planner (`create`/`update`/`skip`/`block` items with reason codes).
4. Preview; require explicit `--yes` or interactive confirmation (EOF is refusal).
5. Apply through the existing `ApplyRestorePlan` boundary under the workspace write lock, which
   after AT114-506 evaluates the `backup_restore` governance policy before writing (§2.2); a denying
   policy is exit 5 with zero writes. Then `reindex` and `doctor`.

The user's source repository is never reset or checked out.

## 6. Threat model

| # | Threat | Mitigation | Enforced in | Test (sprint) |
| --- | --- | --- | --- | --- |
| 1 | Source-code capture | Fixed candidate list + restore-safe allowlist; `.git`, source, and non-canonical files can never enter the tree | shared snapshot builder | tree of a workspace containing source files has only allowlisted paths (114.4) |
| 2 | Secret capture | Exclusion by path only: private keys, runtime, mutations, local state, index, `.log`, and every non-candidate path are never read; local state lives outside the workspace. No content transformation or redaction is applied, so a secret pasted into a ticket body or comment is backed up as written (the redaction *rules* under `.tracker/redaction` are themselves canonical data and are included); the confidentiality boundary for such content is rule 7 | builder + local-state location | workspace with `.tracker/security/keys/private` and `.env` yields none of them; a ticket body is byte-identical in the tree (114.4) |
| 3 | Credential-bearing remote URL | URL userinfo rejected at target configuration and again before every push; tokens come only from the credential helper/agent | target validation | `https://user:token@host/r.git` rejected (114.5) |
| 4 | Public repository selection | Target creation requires the `visibility_attestation: private` acknowledgment and shows the data boundary; `origin` is never offered as a default | target configuration UX | missing attestation fails; origin never appears in suggestions (114.5) |
| 5 | Git index contamination | `GIT_DIR` = Atlas bare repo, temp index, plumbing only, cwd = temp snapshot dir; user's `.git` never opened | Git runner | user repo `HEAD`, index, staged/unstaged/untracked, and in-progress rebase are byte-identical before/after (114.4) |
| 6 | Git lock interference | Atlas never creates `.git/index.lock` or ref locks in the user's repository; its own repo has its own locks; the exclusive workspace write lock is held only while copying the candidate files and the checkpoint yields (`busy` → retry) to a concurrent writer | Git runner + builder | checkpoint while a user `git rebase` is in progress succeeds and leaves the rebase state intact; a checkpoint racing a `ticket move` retries and the mutation succeeds (114.4) |
| 7 | Symlink escapes | Collector rejects symlink entries; tree entries restricted to `100644` blobs; restore rejects `120000`/`160000` entries | builder + restore verifier | symlinked ticket dir and a crafted symlink tree entry both rejected (114.4/114.5) |
| 8 | Path traversal | `isSafeRestorePlanPath`: no absolute, no `..`, no NUL, cleaned == given, allowlisted prefix and suffix | contracts + restore verifier | crafted manifest with `../` and absolute paths blocked (114.5) |
| 9 | Backup recursion | No canonical events from checkpoints; `.tracker/backups/*` excluded; outbox lives outside the workspace; tree-hash equality short-circuits | §4.4 + builder | two consecutive ticks with no mutations produce no second commit (114.4) |
| 10 | Remote divergence | Expected-tip check before push; non-fast-forward is `diverged`, never forced; `backup reconcile` creates a new replica ref | publisher | remote advanced by another writer yields `diverged` and no force (114.5) |
| 11 | Multiple replicas | Per-replica refs; copied workspace requires reconcile; restore lists all replicas | replica model | two replicas push concurrently without conflict (114.5) |
| 12 | Interrupted push | Local commit exists before push; verification runs after; an unverified push is retried idempotently (same commit, same ref) | publisher + ledger | kill during push, next tick verifies or re-pushes the identical commit (114.5) |
| 13 | Malicious checkpoint | Full verification in §5 step 2 before any path is materialized; only allowlisted `100644` blobs; hash and count checks; size limit | restore verifier | tampered blob, extra entry, wrong workspace ID, oversized tree all refused (114.5) |
| 14 | Restore into conflicting state | Existing restore planner produces `block` items with reason codes; apply refuses when blocked; pre-destructive checkpoint taken first | restore planner | conflicting ticket edits produce `block` and apply is refused (114.5) |
| 15 | Ransomware / local workspace deletion | Remote history is append-only under the replica ref; restore into a fresh workspace with explicit mismatch acknowledgment; recovery drill documents the sequence | provider + drill | delete workspace, restore from remote, `doctor` ok (114.5 drill) |
| 16 | SSH host-key trust on first connection | `GIT_TERMINAL_PROMPT=0` and `BatchMode=yes` turn an unknown host into a failed connection, never a silent accept: the failure is classified `host_key_unverified` in `backup status` with the exact host, and the user establishes trust with their own `ssh` session (Atlas never writes `known_hosts` and never passes `StrictHostKeyChecking=no` or `accept-new`) | publisher error classification | unknown host yields `host_key_unverified`, no push, no `known_hosts` change (114.5) |
| 17 | Backup target is the workspace's own project remote | Target configuration compares the URL with the workspace repository's remotes and warns (§3.3); `backup status` repeats the warning; per-replica refs under `refs/atlas/*` never touch branches or tags, but a mirror push or ref prune from another clone can delete them, so the recovery drill treats a vanished ref as `remote_ref_missing` and re-publishes the full chain | target configuration + publisher | target equal to `origin` yields the warning; deleted remote ref is detected on the next verify and re-pushed (114.5) |
| 18 | Restore without governance | `ApplyRestorePlan` evaluates the `backup_restore` protected action before writing (§2.2) | service boundary | denying policy → exit 5, zero files written; allowing policy → unchanged behavior (114.5, AT114-506) |

## 7. Consequences and dependencies

- AT114-401 (shared snapshot builder) is a `[SHARED]` change to `internal/service`: the candidate
  list gains collaborators, memberships, mentions, and archive records with Markdown payloads
  (§2.1), the parity test is added, and the checkpoint copy runs under the exclusive write lock
  with a bounded hold (§3). Any allowlist widening in `internal/contracts/backup.go` waits for the
  AT114-507 drill evidence. One integration owner.
- The `commitMutation` hook (AT114-402) is a `[SHARED]` change to `internal/service/action.go`.
- The Git runner (AT114-403) is new code with no external dependency: it shells out to the
  system `git` through the structured command model (no shell interpolation) with the pinned
  `-c` settings of §3.2 and without masking the user's credential configuration.
- AT114-506 adds the `backup_restore` governance evaluation to `ApplyRestorePlan` (§2.2), a
  `[SHARED]` change with the two tests named there.
- No change to the existing `sync`, archive, or signature subsystems.

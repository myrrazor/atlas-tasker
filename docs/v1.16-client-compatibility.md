# Atlas Tasker v1.16 client compatibility

The matrix below separates native skill discovery, MCP configuration, and actual agent tool calls. Use it alongside the [upgrade guide](migration-v1.16.md) when connecting an existing workspace.

Atlas writes files and argv. A file under a documented directory is
**installed guidance**, not proof that the client listed the skill, started
MCP, or ran a ticket workflow. Atlas does not start agents, grant client
trust, or mark a client connected because a config file exists.

The checks below are **representative local-client proof** on named versions
with synthetic, isolated configs. They are not a claim that every client
version, cloud/remote agent, or global auto-registration path is seamless.
Hermetic Atlas writes of skills and argv were verified in isolated `HOME`
fixtures; those writes did not start a live client session.

## Five facts

Keep these separate. Do not promote a weaker category to a stronger one.

| Fact | What it proves | What it is not |
|---|---|---|
| Installed guidance | An Atlas-managed `SKILL.md`, instruction block, or extra file exists on disk | The client loaded or listed it |
| Native listing (discovered) | A named client version listed the skill (Codex `skills/list`, Grok inspect after trust) | MCP tools or a model turn |
| Configured MCP | An Atlas-managed `atlas-tasker` (user) or project entry matches expected argv | `initialize` or `tools/list` succeeded |
| Connected | Live `initialize` and `tools/list` (or that client's equivalent probe) against the named version | A model used those tools |
| Model workflow | A real model-driven ticket loop through Atlas MCP | File write, listing, or a refused tool call |

`tracker init` writes user-scoped **`atlas-tasker`** with
`mcp serve --global --tool-profile workflow`. Grok also gets
`--tool-name-style portable`. Advanced `tracker setup` still writes a
workspace-bound server (`--expected-workspace-id`, never `--global`). Matching
argv means the same flags for the same scope, not collapsing those two scopes.
Pinned `--workspace` snippets in this repo are the advanced alternative.

`tracker integrations install` writes skill and instruction files. It does
**not** register MCP. Editor MCP still comes from `tracker init` (or the
documented scoped `tracker setup`).

## Native skill roots

Canonical Atlas **write** paths. A write is installed guidance only.

| Target | Canonical write | Other documented walk paths | Leftover migration |
|---|---|---|---|
| Claude Code | `.claude/skills/atlas-worker/` | — | — |
| Codex | `.agents/skills/atlas-worker/` | `.codex/skills/atlas-worker/` still lists on Codex CLI 0.144.5 | Delete that leftover only when the file is **byte-identical** to a known generated Atlas skill (current or v1.15 body) |
| Cursor | `.cursor/skills/atlas-worker/` | Project `.agents/skills`; compatibility `.claude/skills` and `.codex/skills` | — |
| OpenClaw | `.agents/skills/atlas-worker/` | — | — |
| Grok | `.grok/skills/atlas-worker/` | User `~/.agents` is client-owned; Atlas does not write it or repo `.agents` | `.tracker/integrations/grok-agent-skill/` is not a Grok listing root; same exact-byte leftover rule |
| Generic | `.tracker/integrations/generic-agent-skill/` | — | `.tracker/integrations/atlas-agent-skill/` is left untouched |

Implementation: `internal/integrations/native_skills.go`
(`LegacySkillRemovals`, `exactGeneratedLegacyFile`, `workspacePathUnlinked`).
Detection: `internal/integrations/detect.go`.

### Codex CLI 0.144.5 (native listing)

Metadata-only app-server `skills/list` (no model turn) listed `atlas-worker`
from:

- `.codex/skills/atlas-worker/SKILL.md` when only that copy existed
- both `.agents/skills/atlas-worker/SKILL.md` and `.codex/skills/atlas-worker/SKILL.md` when both existed, as two entries with the same name

`.codex/skills` is still a working Codex root. Migration is
**canonicalization**: write `.agents/skills`, then delete a leftover under
`.codex/skills` only when that file is byte-identical to a known generated
Atlas skill. It is not repair of a dead path. A leftover that still has Atlas
markers but extra user text is kept and reported as a collision. Atlas does
not follow leftover symlink chains; those paths are collisions too. Ordinary
refresh of an Atlas-owned skill on the canonical path is still a full rewrite
of generated files; that is not “retaining user edits.”

### Grok Build 1.0.30 (native listing + client-owned trust)

An untrusted project returns no local instructions or project skills even when
`.grok/skills/atlas-worker/SKILL.md` is in the correct place. After accepting
Grok's native project-trust prompt for that repo, inspect lists `atlas-worker`
at that path.

That is native listing proof, not MCP initialize and not a model workflow.
Atlas does not write Grok project trust.

### Shared `.agents` ownership

Codex and OpenClaw share one `atlas-worker` SKILL.md under `.agents/skills`.
The shared copy carries OpenClaw `requires.bins` metadata (Codex ignores unknown
metadata). Codex-only extras (`agents/openai.yaml`) and OpenClaw-only extras
(`commands/`) sit beside it. Uninstall of one keeps `SKILL.md` while the other
still has its managed `AGENTS.md` block. Unrelated user files in that directory
are not overwritten.

Cursor is not given a second Atlas write into `.agents`. Cursor docs also walk
`.agents`, `.claude`, and `.codex`. Duplicate `atlas-worker` listings across
those Cursor compatibility roots are **not verified**; do not claim they are
avoided. Cloud Cursor does not automatically receive global `~/.cursor` files.

## Init vs setup argv

User-scoped init (`atlas-tasker`):

```text
<tracker> mcp serve --global --tool-profile workflow
```

Grok adds `--tool-name-style portable`. Cursor init writes that argv into
`~/.cursor/mcp.json` when `cursor` or `cursor-agent` is detected. A matching
file is `pending_client_restart` / configured, never connected.

Project-scoped setup keeps the adapter registration: workflow profile, workspace
binding, `--expected-workspace-id`, Grok portable names. It does not copy
`--global`. Codex project MCP still stops at workspace trust; Atlas never
writes a trust bypass. Grok skill listing has a separate native project-trust
prompt.

## MCP schemas: empty `required` is an array

OpenClaw 2026.9.2 `mcp add` against **v1.15.0** parsed argv and then rejected
`tools/list` because many `inputSchema.required` values were JSON `null`. JSON
Schema / MCP needs an array or omission.

v1.16 emits `[]` when a tool has no required fields and keeps named
required lists as arrays (`internal/mcp/schema.go`, `objectSchema`). There is
no recursive schema rewrite. Native OpenClaw 2026.9.2 `mcp add` / probe against
this candidate then listed **94** tools. That unblocks listing; it is not a
model-workflow proof.

### What the live checks actually did

- **Grok 4.6 xhigh** used the `atlas-candidate` MCP server to register
  `agent:grok-native`, create `APP-1`, claim a work lease, comment, and read
  history back. Claim did **not** change ticket status; it stayed `backlog`.
- **Claude Code 2.1.259** with a strict isolated MCP config called
  `status`, `project.list`, created `APP-1`, and read it back.
- **Codex CLI 0.144.5** with `--ignore-user-config` and an explicit fixture
  MCP completed `status` and `project.list`. The client canceled
  `ticket.create`; there is no successful write proof on this Codex run.
- **Cursor CLI `2026.09.10-fd3934a`** listed 94 native tools from project
  `mcp.json` only after the normal `mcp enable atlas-native` approval.
  No model workflow. No Cursor GUI or Cursor Cloud proof.
- **OpenClaw 2026.9.2** native `mcp add` / probe succeeded against the
  candidate after the schema fix (94 tools). No bot or agent model turn.

Empty or “not claimed” cells are not passes.

## Anonymous installer (published v1.15.0)

`gh` remains a prerequisite. The candidate installer verified a **public
v1.15.0** archive with an empty GitHub config directory and no GitHub token:
checksum plus `gh attestation verify --bundle` against pinned
`--repo myrrazor/atlas-tasker`,
`--signer-workflow myrrazor/atlas-tasker/.github/workflows/release.yml`, and
`--source-ref refs/tags/v1.15.0`. That path does not need a GitHub login.

Hosted verification of the v1.16 attestation-bundle release asset is recorded on the
[v1.16 release page](https://github.com/myrrazor/atlas-tasker/releases/tag/v1.16.0). `tracker update` still uses online
`gh attestation verify` without `--bundle`. Details:
[v1.16 installer contract](v1.16-installer-contract.md).

## Client-owned prerequisites (not Atlas)

- Restart or new session after MCP/skill file changes (Codex new session;
  OpenClaw gateway reload; Grok new session; Cursor restart still unverified
  for GUI).
- Codex workspace trust before `.codex/config.toml` is loaded (MCP).
- Grok native project trust before `.grok/skills` appears in inspect.
- Claude project `.mcp.json` trust then per-server approval when that scope is used.
- Cursor `mcp enable <server>` (or the GUI equivalent) before `list-tools`.
- Cursor enterprise MCP allowlists may block the server.
- Cloud / remote agents do not automatically see global skill or MCP files.
- User `~/.agents` (Grok) and unmanaged files in skill dirs stay client-owned.

## Operator verification (local, no hosted agents)

These steps prove files and argv on this machine. They do not by themselves
prove a live client session.

1. Confirm the binary. The published one-liner is still v1.15.0. A source or
   source build reports `"version": "dev"` unless stamped.
2. In a directory named `app`: `tracker init`, then restart detected clients.
3. Confirm skill files at the canonical roots above. Presence is installed
   guidance only.
4. Confirm the user MCP entry is named `atlas-tasker` and uses
   `--global --tool-profile workflow` (Grok also `--tool-name-style portable`).
   Home → Settings → Agents shows `written` / `pending_client_restart` /
   `unverified`. That is not connected.
5. Grok: accept the client's project-trust prompt, then inspect. Before trust,
   local skills stay hidden.
6. Codex 0.144.5: `skills/list` may show `.agents` and leftover `.codex`. One
   managed copy is the goal; both list as duplicates.
7. OpenClaw: do not treat a v1.15 `tools/list` rejection as a missing binary.
   Re-run native `mcp add` against v1.16; record initialize separately
   from a model turn.
8. Cursor CLI: Atlas can write `mcp.json` when `cursor` or `cursor-agent` is
   on PATH. `list-tools` still needs the client's MCP enable/approval step.
9. After `tracker update`, re-run `tracker init` or the documented scoped
   `tracker setup` / `tracker integrations install` **inside each workspace**.
   Update replaces the binary only. Skills do not refresh automatically.
   `integrations install` still does not register MCP.

Cold-use fixture after a local build:
`python3 scripts/verify-integration-discovery.py --tracker ./tracker`.
It uses an isolated `HOME` and a fixture-only `PATH`, and never touches the
operator's real client config. It proves installed guidance and
detection/argv contracts. It does not start Grok, Codex, Cursor, Claude, or
OpenClaw sessions.

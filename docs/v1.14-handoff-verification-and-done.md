## Manual verification before v1.14

Automated adapter tests are necessary but not sufficient.

### Agent setup drill

On a clean macOS user account or VM:

1. Install all available named clients.
2. Install the exact Atlas release candidate.
3. Initialize a clean repository.
4. Run `tracker setup`.
5. Select Codex, Claude, Cursor, OpenClaw, Grok, and generic.
6. Verify each generated skill.
7. Verify each MCP registration.
8. Complete any unavoidable provider trust step.
9. Restart clients where required.
10. Ask each client for the board.
11. Perform one workflow mutation with each.
12. Run integration status.
13. Repair one deliberately broken registration.
14. Disconnect each provider.
15. Confirm unrelated provider configuration remains.

### Managed project drill

1. Give an agent a coding task without mentioning a ticket.
2. Confirm it searches Atlas.
3. Confirm it creates or reuses the correct ticket.
4. Confirm it claims and starts the ticket.
5. Ask for an update.
6. Confirm the response comes from current Atlas data.
7. Ask another agent to review.
8. Confirm identities and review separation.
9. Complete the task.
10. Confirm the board and event history agree.

### Backup disaster drill

1. Configure a private backup remote.
2. Perform ticket moves, comments, assignments, reviews, and completion.
3. Confirm the mutation response does not wait for the network.
4. Confirm an automatic checkpoint is created.
5. Confirm the remote ref is verified.
6. Disconnect the network and perform more mutations.
7. Reconnect and confirm catch-up.
8. Delete the local test workspace.
9. Restore into a new directory.
10. Reindex and run doctor.
11. Compare canonical manifests.
12. Confirm no source code, keys, remote credentials, runtime state, or local approvals were
    restored.

## Final v1.14 definition of done

Atlas Tasker v1.14 is ready only when all of the following are true:

- `tracker setup` is idempotent and repairable.
- All six target adapters are implemented.
- Codex MCP registration is verified.
- Claude MCP registration or pending approval is represented accurately.
- Cursor MCP registration is verified.
- OpenClaw live probe is verified.
- Grok project MCP registration is verified.
- Generic portable integration passes its conformance test.
- The existing atlas-worker skill drives managed project behavior.
- "What is the status?" retrieves live Atlas data.
- "Show me the board" produces the correct project board.
- Agent writes use correct identities and policy.
- High-impact tools remain disabled by default.
- Automatic local checkpoints do not touch user Git state.
- Off-device checkpoints use an explicitly configured target.
- Remote verification proves the expected commit is present.
- Backup failures do not block ordinary ticket operations.
- Multi-replica histories do not conflict.
- Remote restore uses the existing verified restore-plan/apply boundary.
- A clean disaster-recovery drill passes.
- v1.13 upgrades without losing integrations or backups.
- Clean installation passes on supported platforms.
- Independent review reports no unresolved P0/P1.
- Exact source, binaries, test evidence, and recovery evidence are cryptographically bound to one
  release candidate. *(Procedural binding waived as a gate by owner override; functional evidence
  still required.)*
- Release publication receives a separate explicit owner decision.

## Master implementation instruction

> Originally addressed to Codex. The owner has since delegated implementation to Cursor; the
> instruction content stands unchanged.

Implement Atlas Tasker v1.14.0 as the Seamless Agent Setup and Automatic Verified Backup release.

Use the approved exact repository baseline. Work in a new isolated branch and worktree. Preserve
unrelated dirty checkouts. Do not begin from a floating branch head.

Implement the seven sprint gates and 45 tickets described in the approved v1.14 plan. Work sprint
by sprint. Do not collapse all work into one unreviewed implementation pass.

The release must support all six existing integration targets: codex, claude, cursor, openclaw,
grok, generic.

Do not create a second agent-management skill. Extend the existing atlas-worker skill and
provider-specific managed instruction blocks.

The high-level user path must be:

1. `tracker setup` detects the workspace and installed agents.
2. The user selects agents and managed mode.
3. Atlas installs or refreshes the existing skill.
4. Atlas registers a project-bound Atlas MCP server for every supported selected client.
5. Atlas maps each provider to an explicit Atlas agent identity.
6. Atlas verifies each registration and reports connected, restart required, pending approval,
   portable ready, unsupported, repair required, or failed.
7. Atlas optionally configures automatic backup under a separate consent.
8. Atlas creates and remotely verifies the first checkpoint.
9. `tracker setup status` reports the complete resulting state.

Use MCP tool-profile `workflow` by default. Never enable `delivery`, `admin`,
`dangerously-allow-high-impact-tools`, or permanent high-impact approvals in ordinary setup.

Provider requirements:

- Codex: project-scoped `.codex/config.toml` and native status verification.
- Claude Code: local-project or explicit project scope with native add/get/list verification;
  preserve approval and trust requirements.
- Cursor: `.cursor/mcp.json` with project-safe workspace resolution.
- OpenClaw: uniquely namespaced workspace server plus `mcp doctor --probe`.
- Grok: native project-scoped MCP registration and JSON doctor/inspect proof.
- Generic: portable MCP descriptor, existing generic skill, conformance host, optional custom
  config adapter, and no false connected claim.

Add a safe project-context MCP launch mode only when required. It must require an expected
workspace ID, reject nested or symlinked ambiguity, never initialize a workspace, and never fall
back to another registered workspace.

Add managed project mode. The existing skill must:

- query Atlas at the start of material work;
- search before creating a ticket;
- use an explicitly named ticket;
- claim/start work legally;
- record milestone progress and evidence;
- follow dependency, governance, review, and completion policies;
- query Atlas before status responses;
- reconcile Atlas before reporting completion.

Add read-only `atlas.context` and `atlas.status` tools. `atlas.status` must support workspace,
project, ticket, agent, and run scopes, return bounded structured content, deterministic Markdown,
blockers, review state, next actions, recent changes, and backup health. Add a read-only
progressive MCP App board where supported, with Markdown as the universal fallback.

Automatic backup must not commit to the user's branch. It must:

- reuse the existing canonical backup collector and restore machinery;
- write Atlas-owned state only;
- keep an Atlas-owned bare Git repository outside the workspace;
- preserve the user's HEAD, branch, index, staged, unstaged, and untracked files exactly;
- maintain a durable reconstructable outbox;
- debounce for 30 seconds;
- enforce a five-minute maximum unbacked delay;
- checkpoint at 100 pending events;
- use a workspace and replica-specific backup ref;
- push fast-forward only;
- never force push, merge, pull, or auto-restore;
- never select the existing origin automatically;
- reject credential-bearing URLs;
- use existing SSH-agent or credential-helper authentication;
- verify the exact remote commit, tree, and manifest after push;
- keep ordinary Atlas mutations successful during remote failure;
- classify and expose degraded backup states;
- prevent backup events from recursively triggering backups.

Add explicit user-level backup execution through `backup tick`, `backup watch`, and consented
launchd/systemd user scheduling. No root and no hidden service from `tracker init`.

Remote restore must fetch into temporary storage, verify commit/tree/manifest, materialize only
Atlas-owned paths, use the existing restore-plan/apply boundary, require explicit confirmation,
rebuild the SQLite projection, and run doctor. It must never reset or check out the user's source
repository.

Implement transactional provider configuration with plan, snapshot, apply, verify, rollback,
repair, and remove. Preserve unrelated config content. Reject symlinked, unsafe, malformed,
changed-after-plan, or ambiguously owned configuration. Remove only exact Atlas-owned entries.

Add complete deterministic tests, real-client allowed-host tests for every named provider, a
generic MCP conformance host, concurrent agent tests, crash injection, Git-isolation tests,
multi-replica tests, offline/retry tests, malicious-checkpoint tests, scale tests, and a clean
disaster recovery drill.

After every sprint:

- create one clean immutable candidate;
- run focused and full applicable tests;
- run security and secret scans;
- obtain an independent source review;
- fix every P0/P1;
- rerun and re-review;
- record evidence (procedural SHA-binding waived by owner override; functional evidence required).

Do not begin the next sprint until the current gate is cleared.

Do not publish, tag, release, create a remote repository, use a public backup target, or perform
any irreversible external action without separate explicit owner authorization.

## Verification notes (Sprint 114.0)

Provider claims in the plan were checked against official documentation on 2026-09-10. The
following verified facts refine plan assumptions and govern the adapters in Sprint 114.2. The full
per-provider matrix, with the source of each fact, is in
[docs/v1.14-provider-adapter-contract.md](v1.14-provider-adapter-contract.md).

- **Codex.** Project-scoped `.codex/config.toml` is loaded only for projects the user has marked
  trusted (`projects.<path>.trust_level`), which maps to `pending_workspace_trust`. The
  `codex mcp add/list/get/remove` CLI operates on the user-level `~/.codex/config.toml`
  (`$CODEX_HOME`); the project-scoped table must be written by Atlas as a TOML edit and can be
  inspected with `codex mcp list`/`codex mcp get` from a trusted project directory.
  `mcp_servers.<name>.required` (default false), `enabled`, `cwd`, `startup_timeout_sec`
  (default 10s), `tool_timeout_sec` (default 60s), `enabled_tools`/`disabled_tools`, and
  `default_tools_approval_mode` (`auto | prompt | writes | approve`) are documented keys. The
  official reference describes project files as "project-scoped overrides" of the user layer.
- **Claude Code.** Scopes are `local` (default; `~/.claude.json` keyed by project path),
  `project` (`.mcp.json`), and `user`. Precedence is local > project > user, with no field merging
  across scopes. Project-scoped servers show `⏸ Pending approval` until the workspace is trusted
  and the server approved interactively; `disabledMcpjsonServers` rejects a server everywhere;
  `claude mcp reset-project-choices` clears decisions. Re-adding an existing name at the same
  scope fails ("already exists"), so apply must detect existing entries rather than retry. Server
  names `workspace`, `claude-in-chrome`, `computer-use`, `Claude Preview`, and `Claude Browser`
  are reserved.
- **Cursor.** `.cursor/mcp.json` (project) and `~/.cursor/mcp.json` (global) are merged with the
  project entry winning on a name collision. Cursor resolves `${workspaceFolder}`,
  `${workspaceFolderBasename}`, `${userHome}`, `${env:NAME}`, and `${pathSeparator}` in
  `command`, `args`, `env`, `url`, and `headers`. MCP Apps are supported with automatic fallback to
  normal responses; at the time of verification, widgets from project-scoped servers had a known
  issue where `resources/read` is not issued and the result falls back to text. AT114-305 must
  treat Markdown as the primary presentation for Cursor project-scoped registrations.
- **OpenClaw.** Registration is `openclaw mcp add <name> --command ... --arg ... --cwd ...`;
  removal is `openclaw mcp unset <name>` (fails if absent). `doctor` is static, `doctor --probe`
  and `probe` open a live session; `--json` is available on `list`, `show`, `status`, `doctor`,
  and `probe`. `openclaw mcp reload` disposes cached runtimes for the current CLI process only;
  Gateway or agent processes need their own reload or restart, which maps to
  `connected_restart_required`. `doctor` warns on literal sensitive `env`/`header` values.
- **Grok Build.** `grok mcp add --scope project` writes `.grok/config.toml` in the current
  directory; Grok walks from cwd to the git root reading each `.grok/config.toml`, and a project
  server with the same name replaces a user server entirely. `grok mcp list --json`,
  `grok mcp doctor [name] --json`, and `grok mcp remove <name>` exist; `grok inspect` shows every
  loaded server and its origin. Grok also imports MCP definitions from `~/.claude.json`,
  `.cursor/mcp.json`, and project `.mcp.json` below `config.toml` in priority unless
  `[compat.claude] mcps = false` / `[compat.cursor] mcps = false`, which is the duplicate-catalog
  risk AT114-207 must handle. Project `.grok/config.toml` contributes only `[mcp_servers]`,
  `[plugins]`, and `[permission]`.
- **Result-bounding flags.** `tracker mcp serve` in v1.13.0 already accepts `--max-items`
  (default 50), `--max-result-bytes` (default 131072), and `--max-text-tokens-estimate`
  (default 4000) in `internal/cli/mcp.go`. The canonical registration's `30` and `65536` are
  deliberate tightenings of those defaults, not new flags.

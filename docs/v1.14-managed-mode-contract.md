# Managed Project-Mode Contract (AT114-004)

Status: Sprint 114.0 contract artifact, revised after independent review round 1 (findings M-A,
M-B, M-C; dispositions in [release/v1.14-s0-review-round1.md](release/v1.14-s0-review-round1.md)).
Types and validation live in `internal/contracts/managed_mode.go`; the storage helper, `tracker
setup` integration, skill wording, and MCP exposure are Sprint 114.3 (AT114-301..304). Recorded as
DEC-073 and revised by DEC-080 in [v1-decision-log.md](v1-decision-log.md).

## 1. The document

```json
{
  "format": "atlas_managed_mode_v1",
  "mode": "managed",
  "capture_policy": "material_work",
  "progress_policy": "milestones",
  "status_policy": "atlas_required",
  "completion_policy": "follow_workspace",
  "mcp_preferred": true
}
```

That is `contracts.DefaultManagedModePolicy().Encode()` byte for byte (two-space indent, trailing
newline, seven fields in this order). Location: `.tracker/managed-mode.json`
(`contracts.ManagedModeFileName`). The file is workspace-shared and may be committed: it contains
no machine paths, no credentials, and no actor identity.

`ManagedModePolicyForMode(mode)` returns the recommended policy for one valid mode and an error for
anything else, so no caller ever holds a policy that later fails `Validate` (review finding M-B).
`DefaultManagedModePolicy()` is the `managed` recommendation.

`ParseManagedModePolicy` uses `DisallowUnknownFields`, rejects trailing documents, and validates.
A field such as `"skip_review": true` or `"self_approve": true` cannot be added without a new
format version and a corresponding contract change.

## 2. Vocabulary

| Field | Values | Notes |
| --- | --- | --- |
| `mode` | `guidance`, `managed`, `delivery`, `disabled` | `guidance` = skills only (`UsesMCP() == false`); `managed` = skills, MCP, status, ordinary workflow (default); `delivery` = additionally allows separately enabled advanced operations, `RequiresExplicitEnable()`, never a setup default, effective only with machine-local enablement (§2.1); `disabled` = no automatic tracking |
| `capture_policy` | `never`, `ask`, `material_work` | when an agent may create/attach a ticket |
| `progress_policy` | `none`, `milestones`, `every_checkpoint` | how often progress comments are recorded |
| `status_policy` | `atlas_required` | every status answer follows a fresh Atlas read; a failed read is reported, never guessed around |
| `completion_policy` | `follow_workspace` | completion/review/approval follow the workspace and project `CompletionMode` exactly |
| `mcp_preferred` | bool | prefer MCP tools, CLI as fallback |

Cross-field rules in `Validate()`: `disabled` requires `capture_policy = never`,
`progress_policy = none`, and `mcp_preferred = false` (disabled mode registers no server, so a
document that prefers MCP is contradictory; review finding M-A); `guidance` requires
`mcp_preferred = false`.

### 2.1 Delivery is enabled machine-locally

The shared document travels with the repository: a clone, an import, or a backup restore arrives
with whatever `mode` was committed. If `delivery` took effect from the file alone, "requires an
explicit enable" would be a property of the first committer, not of the machine running the agent
(review finding M-C). The contract therefore layers the decision:

- The shared file may declare `mode: delivery`; it parses and validates like any other mode and is
  reported as declared.
- `ManagedModePolicy.EffectiveMode(deliveryEnabledLocally)` returns the mode agents follow on this
  machine. It is `delivery` only when the shared file declares it **and** this machine's private
  setup state records the separately registered delivery-profile server (plan locked decision 3;
  the explicit power-user action of §5). Without that record a declared `delivery` is followed as
  `managed`. Local enablement never upgrades a non-delivery declaration.
- `ManagedMode.AllowsDelivery()` is meaningful only on the value `EffectiveMode` returns; callers
  never read it from the shared document's declared mode.

The `atlas.context`/`atlas.status` tools (AT114-303/304) report both the declared and the effective
mode so a human can see when a repository asks for more than the machine has enabled.

Plan spelling reconciliation: AT114-004's example says `"status_policy": "query_atlas"`, while
AT114-301 and the setup-manifest example say `atlas_required`; AT114-301 says
`completion: follow_workspace_policy`, while the AT114-004 example says `follow_workspace`. The
contract keeps one spelling each (`atlas_required`, `follow_workspace`) and rejects the others, so
a stored document has a single vocabulary. The plan text is left as approved.

## 3. Material work and ticket capture

`WorkIntent` classifies the request; the skill (AT114-302) and `atlas.context` (AT114-303) use it.

| Intent | Trackable | Meaning |
| --- | --- | --- |
| `material_work` | yes | expected to modify the repository, create an implementation artifact, run a substantive review, or produce a durable project deliverable |
| `status_query` | no | "what is the status", "what is blocked", "show me the board" |
| `read_only_explanation` | no | explaining code or state without changing anything |
| `casual_discussion` | no | conversation with no project change |
| `simple_question` | no | a question whose answer changes nothing |
| `tracking_excluded` | no | the user explicitly asked not to track this work; wins over every policy |

`ManagedModePolicy.CaptureDecision(intent)`:

| Condition | Decision |
| --- | --- |
| intent not trackable, or mode `disabled` | `no_ticket` |
| `material_work` + capture `never` | `no_ticket` |
| `material_work` + capture `ask` | `ask_user` (a ticket the user named may still be used) |
| `material_work` + capture `material_work` | `attach_or_create`: search first, use the ticket the user named, create only when none matches |

`RecordsProgress(event)`: `none` never; `milestones` on `milestone` events only (tests passing,
review requested, deliverable produced); `every_checkpoint` on both; `disabled` never.

## 4. Authority boundaries (acceptance of AT114-004)

- **Existing completion and review policies remain authoritative.** `EffectiveCompletionMode(ws)`
  returns the workspace mode unchanged and errors on an invalid one instead of falling back to
  `open`. The policy has no field that names a reviewer, approver, or gate.
- **Managed mode cannot waive dependencies, governance, review, or approval.** The document has
  exactly seven fields; unknown fields fail parsing. Dependency blocking, governance packs,
  separation of duties, and approval gates are enforced by the existing service layer on every
  write and are not consulted by this contract at all, so there is nothing to waive.
- **Agent identity is always explicit in writes.** The policy carries no actor. The provider's
  Atlas actor comes from the integration's `ActorHint` (AT114-209) and every CLI/MCP write still
  requires `actor` and `reason` exactly as in v1.13.
- **No silent self-approval.** Because completion follows the workspace mode, an agent in
  `review_gate` or `dual_gate` still needs the configured reviewer; the existing permission checks
  (exit 5 / `permission_denied`) apply unchanged. The skill text in AT114-302 must say so.

## 5. Consequences for later sprints

- AT114-301 adds `storage.ManagedModeFile(root)` and read/write through the normal write lock
  (taken after the setup lock when written by `tracker setup`, see the transaction model §3), and
  must extend the export candidate list and the restore-safe allowlist so the file is included in
  backups ([backup ADR](v1.14-automatic-backup-adr.md) §5, a `[SHARED]` change).
- AT114-302 rewrites the atlas-worker skill around `CaptureDecision` and `RecordsProgress`, and
  reads the mode through `EffectiveMode`.
- AT114-303/304 expose the declared and effective policy in `atlas.context` and `atlas.status`,
  taking `deliveryEnabledLocally` from the private setup manifest's record of a delivery-profile
  server registration.
- `tracker setup --mode` only offers `guidance`, `managed`, `disabled`; `delivery` is reachable
  only through an explicit dedicated command in a later sprint, which both writes the shared
  declaration and records the machine-local enablement.
